## Public repository: no real vault names

This repository is public. Nothing tracked (code, tests, fixtures, docs, code comments, commit messages) may use the real name of one of the owner's vaults, or of a service that feeds one of them, in any spelling: not as a slug, a title, a folder, a path or an example. Use neutral placeholders instead (`my-vault`, `test-vault`, `Notes/My Note`, "the external sync service"). When a test needs a name as data (an accented title, a slug with capitals), pick a neutral one that exercises the same case. The rule deliberately lists no names: a list of them in a tracked file would defeat it. The same goes for anything specific to one machine (absolute paths, hosts, ports), which belongs in a gitignored file.

After ANY change under `builder/`, rebuild **every** vault (`--all`) — build output is per-vault and goes stale silently otherwise.

## Architecture

This is **two programs** sharing one repo:

1. **The builder** (`builder/`) — an ahead-of-time renderer run from the CLI (`npx tsx builder/index.ts`). It reads an Obsidian vault folder from disk and writes prebuilt output to `data/<slug>/`. It does not copy images: it only records which ones the pages cite (`assets.json`), and a route serves them from the vault.
2. **The Next.js viewer** (`app/`, `components/`, `lib/`) — at request time it only **reads** that prebuilt `data/<slug>/` output; it does no markdown rendering. So content changes are invisible until the vault is rebuilt. The exceptions are the comment API and the property API (see Auth, data, config): the first writes comment files into the vault's `_comments/` folder and renders the comment it returns with the restricted render; the second rewrites one property in a note's frontmatter and renders the property row it returns; both then ask for a rebuild.

### Build output contract (`data/<slug>/`)
- `pages/<path>.json` — a `PageMeta` (final HTML + frontmatter + outlinks + per-page CSS; `properties` only on a page with at least one visible property, see `properties.ts` below; `tabs` only on a tab bar's mother and its tabs; `commentable` and `comments` only on a commentable page, see Comments below). A comment (see Child notes below) gets no page JSON.
- `pages-index.json` — `PageSummary[]` (path, title, **file** [basename], tags) for sidebar/search. Child notes (tabs, comments) are left out of it, of `tree.json` and of `graph.json`.
- `tree.json` — the sidebar tree, prebuilt with folder-notes already absorbed (built at build time so the client doesn't recompute 700+ nodes per navigation).
- `graph.json` — `BuildGraph` (nodes + edges; self-loops removed).
- `assets.json` — sorted vault-relative paths (with `/`) of the images the pages cite and that exist as files inside the vault. It is the whole allowlist of the image route (see Auth, data, config). A cited path that isn't a valid path is never looked up (`ImageHandler.resolve`): no filesystem call and nothing in this list, while its URL is written as before (the image is 404). Invalid means a control character (U+0000 to U+001F, NUL included), a character Windows rejects in a file name (`<>:"|?*`), a segment (between `/` or `\`) longer than 255 UTF-8 bytes or a whole path longer than 4,096: `isValidImagePath` in `builder/image-handler.ts`, whose character rule is the one of `safePagePath`, which a test keeps equal. `/` and `\` are separators there, and `..` is still handled by the vault-root check. Why: with a NUL `stat` throws, and one property value would fail the whole vault's build. A `stat` that fails on a valid path (`ELOOP`, `EACCES`, …) counts as a missing file: the cited image stays out of `assets.json` and the build goes on.
- `property-values.json` — the values index of list and single-select properties (`collectPropertyValues` in `builder/plugins/properties.ts`): for every key whose value is a list in some page's rows, the distinct items across the vault, keys and values sorted with pt-BR collation. A single-select row (`select`, see `properties.ts` below) puts its key in the index even when its value is empty, and adds its trimmed value. A key with `select` options in `.vaultwright/properties.json` lists those options first, in the file's order and used or not, then the used values outside them in pt-BR order (a key whose rows are lists too); a configured key that no row uses doesn't enter. It comes from the unlocked rows of every written page, tabs included; comments and anything in `_comments/` never enter, since they get no page. A loose string with a mismatch on a list key (`tags: foo`) enters trimmed. It is written after `assets.json` and before the pruning and `index.json`; the `--first` front doesn't write it. A key can be named `__proto__`, so a reader checks keys with `Object.hasOwn`.
- `index.json` — `pageCount` + `folderCount` + `builtAt` + `startedAt` (the moment just before the vault scan). It is written **last**, after the pages, the indexes, `graph.json`, `assets.json`, `property-values.json` and the pruning, so a new `startedAt` means a build that finished. `folderCount` (shown on the vault card) is the number of folder nodes in `tree.json`, at any depth and after folder notes are absorbed (`countTreeFolders` in `lib/vault-tree.ts`), so it counts only the folders the sidebar shows: never `_comments/`, an empty folder, a folder holding only child notes or only files that aren't pages (images, attachments), or an ignored folder. It comes from the tree, not from a walk of the disk, so the two can't diverge: the old disk count counted every `_comments/<note>/` folder.

Stale pages are pruned: after writing, the builder deletes every `pages/**/*.json` it did not write in this build (compared case-insensitively: on NTFS a case-only rename keeps the old file name on disk, and an exact comparison would delete the page just written) and removes empty folders. A build that found **zero** pages deletes nothing (empty vault folder, unmounted disk).

Types live in `builder/types.ts` and `types/index.ts`.

### Builder pipeline (`builder/pipeline.ts`)
Per page: dataviewjs/DQL are extracted, then a **recursive `renderBody`** runs in this order: dataview → `renderColumns` → `renderCallouts` → `applyObsidianCompat` → `renderCaptions` → wikilinks → `renderMarkdown` (remark/rehype). It's recursive (callouts/columns call `renderBody` on their stripped inner content) which is why dataview/columns/callouts nest correctly. **Order is load-bearing** — e.g. columns before callouts (fences are stronger boundaries than blockquotes); dataview inside `renderBody` so blocks nested in callouts/columns are reached after their `> `/fence prefixes are removed. Plugins are in `builder/plugins/`.

**Page HTML.** A page is `[banner]<article class="vault-content">[title]<properties marker><comments marker><body></article>`. `PROPERTIES_MARKER` (`<div class="vault-properties-slot"></div>`, in `builder/plugins/properties.ts`) is there only when the page has at least one visible property, and `COMMENTS_MARKER` only when the page is commentable (see Comments below). The Properties block itself is no longer in the HTML: it travels as `PageMeta.properties`, and the viewer mounts it at the marker. The property config (`loadPropertyConfig`, see `properties.ts` below) is read once per build, before the `--first` front.

**Frontmatter is read as YAML only** (`parseYamlFrontmatter` in `builder/frontmatter.ts`, the one rule behind the builder's `extractFrontmatter` and the comment API). gray-matter picks its engine from the word after the opening `---`, and its JavaScript engine (`---js`, `---javascript`) runs the block with `eval` on the machine that reads the file. A note that declares any engine other than `yaml`/`yml` (in any case) has an unreadable frontmatter, handled exactly like broken YAML: `{}` as frontmatter and the whole file as body, with nothing in the block run. The declared engine decides, not the block: an empty `---js` block is unreadable too, and so are names gray-matter would find on `Object.prototype` (`---valueOf`, `---constructor`). Why: a file put into the vault by hand, by an agent or by the sync service must not run code through its frontmatter, and Obsidian only reads YAML. dataview/dataviewjs blocks in the body are a separate matter and still run. gray-matter caches only calls without options, so each note is parsed again at each of the pipeline's reads (measured as negligible).

`--first <note path>` (repeatable; `buildVault(vault, { first })`) makes the builder render those notes first and write each `pages/<path>.json` right away, plus `pages-index.json` and `tree.json` once after the first one (same content and order the full build writes), then continue the normal build. Notes changed since the previous build's `startedAt` (`builtAt` in an old `index.json`) go in front too, newest first, after the explicit ones (`builder/first-pages.ts`); without a previous `index.json` only the explicit ones count. The front list is capped at **20**, so a cron run that rewrites hundreds of notes doesn't become "everything first". "Changed" is `noteTime` in `builder/scanner.ts`: `max(mtime, ctime, birthtime)`, ignoring timestamps in the future. `ctime` covers a rename in Obsidian (it keeps `mtime`) and `birthtime` covers a note copied into the vault (it keeps both). This is how the note a user just created is ready in about a second even though the whole-vault build takes several. During the front, `assets.json` is rewritten before each front page as the union of the previous one with the images resolved so far, so a new image opens together with its page; the final one is the exact list. Invariant: the output with `--first` is byte-for-byte the output without it (`index.json` aside).

**Child notes and tabs** (`builder/note-family.ts`). A note with `note_type: tab` or `note_type: comment` and `parent: "[[path/of/mother]]"` is a child note of that mother. Membership is by `parent` alone (the file's folder doesn't matter); it is a vault-root path matched exactly (the exact case first, then case-insensitively; no basename lookup), with or without brackets, dropping alias, heading, `.md` and a leading `/`. `parent` must be a quoted string: unquoted, YAML reads `[[X]]` as a nested list and the note has no `parent`. Only `.md` notes can be mothers. It applies to every vault.
- A child note is left out of the tree, the search and the graph (local and global, so it adds no backlinks): `pages-index.json`, `tree.json` and `graph.json` are built from the listed pages only, and a folder holding only child notes disappears from the tree. Dataview still sees every note, children included, and the link resolver is unchanged (a link to a tab opens it).
- A tab is a page of its own (`pages/<path>.json`), reached through its mother's tab bar. `PageMeta.tabs` is the bar, the same list on the mother and on each of its tabs: the mother first (labelled with its `tab_label`, else its title), then the tabs by `order` ascending (integers only; a tab without `order` goes last), ties by title (pt-BR collation), then by path. A tab's label is its title. One level only: a tab whose `parent` doesn't resolve (orphan), points to itself or to another child note (a tab of a tab, an A↔B cycle) is an ordinary note, visible and without a bar, so nothing disappears silently.
- A comment with a `parent` (resolved or not, even one outside the format such as a list or a number) gets no page and shows up nowhere on its own (its conversation is attached to the mother's page, see Comments below), so a comment body never goes through the full render (which runs dataviewjs): `pageCount` counts tabs but not comments, and the `--first` front never includes a comment. Without a `parent` it is an ordinary note.
- A note without a recognized `note_type` is written exactly as before (no `tabs` key).

**Comments** (`builder/comments.ts`, `builder/comment-render.ts`). The builder attaches `note_type: comment` notes, grouped into conversations, to the page they comment on.
- A page is **commentable** when it has at least one visible property (an empty one counts) and is not a tab of a tab bar (an orphan tab is an ordinary note, so it can be commentable). A note whose keys are all hidden ones (see `properties.ts` below; `note_type` is hidden on every note, so a note with only `note_type: character` is not commentable) has no visible property. Only then does its `PageMeta` get `commentable: true` and its HTML the marker `<div class="vault-comments-slot"></div>` (`COMMENTS_MARKER`) right after the Properties marker, before the body: the viewer puts the comment strip there. Any other page has neither key nor marker and is written as before.
- Conversations follow `parent` (same resolution as child notes): a comment whose `parent` is a non-comment note is a **principal** comment of that note; one whose `parent` is a comment is a reply; a reply to a reply climbs to the principal, so the output has one level of replies. Orphans are dropped (still no page, attached nowhere): a `parent` that doesn't resolve at some step, a cycle, a reply under an orphan, and a mother that isn't commentable (a tab, a note without visible properties).
- `PageMeta.comments` (only with at least one conversation) is `CommentThread[]`, `{ comment, replies }` of `PageComment { path, author, createdAt, updatedAt, body, html }`. `author` is the frontmatter `author` as text (`''` if absent). `createdAt`/`updatedAt` come from `created_at`/`updated_at` normalized to ISO UTC (`toISOString`), `null` when absent or not a date; an unquoted YAML timestamp is already a `Date` (its offset is lost), a quoted one is parsed. `body` is the raw markdown without frontmatter (for editing); `html` is the restricted render. Replies go by `createdAt` ascending; conversations by last activity (the latest `createdAt`/`updatedAt` in the conversation), newest first; `null` last, ties by path.
- **Nothing inside `_comments/` becomes a page or goes through the full render.** `_comments/` is the folder at the vault root where the viewer writes comments, matched case-insensitively, at any depth inside it; `Notes/_comments/x.md` and a root `_comments.md` stay ordinary notes. A valid comment there (`note_type: comment` with a `parent`) is handled as above. Any other `.md` there (an unreadable frontmatter, broken YAML or another engine, which `extractFrontmatter` turns into `{}` plus the whole file as body, a half-written file, a missing or different `note_type`) is ignored: no page, no render, left out of the tree, the search, the graph, `pageCount` and the `--first` front (explicit or not), and never a mother, a tab or a step in a comment chain (a comment whose chain reaches one is an orphan). Dataview still sees those `.md` files. A `.canvas` there gets no page and no render either. It is a safety net: without it, a broken comment file would become an ordinary note and its dataviewjs would run.
- The builder ignores the vault's `comments` flag: comments and `commentable` are always in the output, and the flag is applied at request time (see Auth, data, config).
- **A comment file never fails the build.** Comment bodies are read again from disk when the mother page is rendered; a file that can't be read by then (any error: `ENOENT` when it was deleted while a build runs, `EACCES`, …) is skipped with a warning naming its path, and a missing principal takes its whole conversation with it. A render that throws, or a body past the nesting limit (see the restricted render), shows the fallback instead, with a warning naming the path, and the comment stays in its conversation so its author or an admin can still delete it. The first pass (frontmatter of every note, right after the scan) still fails on a file that disappeared or can't be read, as for any note; the rebuild that follows the deletion fixes it.
- `--first`: a mother's time for the front is the latest of its own and its comments', so a changed comment puts its mother in front. A comment itself never enters the front.
- The **restricted render** (`renderComment(md, { vaultSlug, resolveLink })`) is pure and synchronous, shared by the builder and the API routes. A comment body comes from users, so nothing in it becomes raw HTML or runs. It uses remark-parse + remark-gfm + a local plugin + remark-rehype **without** `allowDangerousHtml` (no rehype-raw, slug or math). Rules:
  - Raw HTML, inline or block, becomes escaped text. remark-rehype alone would drop it silently, so the plugin turns it into text.
  - dataview/dataviewjs fences are plain code, never run. Callouts are plain blockquotes.
  - Images (`![a](x)`, `![a][r]`) and embeds (`![[x]]`) come out as their literal markdown text.
  - GFM footnotes (the reference `[^1]` and the definition `[^1]: ...`) come out as their literal markdown text, with nothing inside the definition interpreted. remark-rehype would give them fixed ids (`user-content-fn-1`), which collide between comments and with the page, and would let a comment hijack in-page anchor navigation.
  - A link becomes `<a>` only with an `http`, `https` or `mailto` scheme, or a relative URL (the micromark `sanitizeUri` rule). Otherwise only its text stays, and a reference definition with an unsafe URL is dropped. `mdast-util-to-hast` doesn't check schemes, so the plugin does. Before the check the URL is cleaned the way a browser's URL parser does (tab, LF and CR removed anywhere; C0 controls and spaces trimmed at both ends), and one that then starts with two characters that are each `/` or `\` is unsafe: browsers read `//host`, `/\host`, `\/host` and `\\host` as protocol-relative, i.e. another site.
  - Wikilinks follow `replaceWikilinks`: href `/vault/<slug>/<encoded path>`, `#heading` slug, dead link `span.vault-dead-link`. They are built as tree nodes, so the alias is always escaped text; `replaceWikilinks` itself doesn't escape it, which is why it isn't reused here. The href goes in `hProperties` so remark-rehype's `normalizeUri` doesn't percent-encode accents in the fragment.
  - A single newline becomes `<br>`, and CRLF is normalized.
  - The tree is walked by hand: `unist-util-visit` is only a transitive dependency.
  - **Nesting limit** (`commentTooDeep(md)`). remark, `mdast-util-to-hast` and `hast-util-to-html` are recursive, so about 3,000 nested `>` in a 10,000-character body overflow the stack; and micromark's emphasis and link-label resolution and the GFM table parse grow with the square of their input, so such a body could cost seconds of CPU. A body is past the limit when some path from the root to a leaf has more than `MAX_COMMENT_NESTING` = 32 levels (a level is a blockquote; a list with its item, counted as one; emphasis, strong, strikethrough, a link or a link reference), when some stretch between blank lines has more than `MAX_INLINE_DELIMITERS` = 500 inline delimiters (`*`, `_`, `~`, `]`), or when the body has more than `MAX_TABLE_CELLS` = 2,000 table cells. A linear pre-check runs first, with no parser (the container markers at the start of each line, where indentation counts as continued list levels, plus the two ceilings; it only errs towards "too deep"); only then the body is parsed and the tree is walked iteratively. The target is under 200 ms for any body up to 10,000 characters. The ceilings can catch a legitimate body (more than 500 task items with no blank line, a huge table).
  - Past the limit, `renderComment` returns `renderCommentFallback(md)`: the body as escaped text (`&`, `<`, `>`, `"`), CRLF normalized, `<br>` at each line break, inside one `<p>`. An optional `onFallback` callback is called (the builder logs it).

Notable plugin behaviors:
- **`dataview.ts`** runs vault DataviewJS in a Node `vm` with a mini-DOM shim (an `El` class, `dv.container`, `document`, `app`). Everything appends to ONE ordered `container` — do not reintroduce a separate output buffer (it scrambles section/gallery order). DQL and `dv.table/list` emit `.dataview-result` placeholder divs that the client hydrates into interactive tables.
  - `executeDataviewJS` is async. As in Dataview, a block containing `await` runs inside an async function, and `renderBody` replaces blocks one at a time (`replaceAsync` in `pipeline.ts`) so captured CSS keeps block order. Output is serialized once, so un-awaited `dv.view`/`dv.io.load` calls are awaited before serializing; the whole thing has a deadline (`timeoutMs`, default 30 s) because a promise that never settles would drain the event loop and make the builder exit 0 without writing anything.
  - `dv.view(name, input)` loads `<name>.js`, then `<name>/view.js`, compiles it **in the block's vm context** (same globals) and passes `(dv, input)`; `<name>/view.css` goes to the page CSS (once per page, even if the view throws). `dv.view` never rejects: every failure becomes an inline `.dataview-error`, so an un-awaited call can't become an unhandled rejection. `dv.io.load(path)` reads a vault-relative file and returns `undefined` when it is missing or resolves outside the vault (as in Obsidian, such a file doesn't exist). Both need `vaultRoot` in `executeDataviewJS`'s options.
  - DOM fidelity that shared renderers rely on: DOM properties that mirror attributes (`href`, `src`, `title`, `value`, …) and boolean ones (`open`, `disabled`, …) are accessors over `attrs`; `classList`; `document.createElementNS` (SVG serialized as-is). `dv.container` is serialized as an element **only** when the script touched it (class/id/attribute), so `.root .x` CSS works and untouched blocks keep their old output. `p.file.frontmatter` is the raw frontmatter; `Date` and `URL` come from the builder's realm so `instanceof Date` matches gray-matter dates.
  - There is no `window` in the context, on purpose: a script shared with Obsidian checks `typeof window` to leave out controls that only work with live events (e.g. a shared gallery renderer drops its reorder buttons and filter pills that way). A gallery participates in the viewer's filter bar by marking `.dv-gallery` / `.dv-card` with an `internal-link` (`data-href` = page path) inside the card.
- **`obsidian-compat.ts`** handles Obsidian-permissive markdown. For emphasis with inner spaces (`**x **`, `** x**`) it **normalizes the markdown** (moves the space outside the marker) and lets remark do the pairing, rather than emitting `<strong>` itself — emitting HTML breaks pairing in chains with links. Adjacency rules run after normalization and must not cross `[]()`.
- **`callouts.ts`** renders callout titles via the full `renderInner` (so titles support markdown/links), and tracks fenced-code regions so example callouts inside code blocks stay literal.
- **`banners.ts`** (`renderBanner`): no frontmatter value reaches the banner's HTML raw, since an editor writes those keys through the Property API.
  - Only a string that cites a vault image counts as a cover: an image wikilink (with or without alias), or a path or file name ending in an image extension, never an `http(s)` URL (`imageTarget` in `properties.ts`, the rule the Properties block uses), and with a valid path (`isValidImagePath`, see `assets.json` above). Any other value (a number, a checkbox, a list, a date, plain text, a path with a NUL) is handled as an empty field: no banner. A valid path to an image that doesn't exist still gives a banner, with a broken image. The resolver gets the raw value, as before, so a cover that counts gives the same URL as before. Without `coverProperty`, a `cover` that doesn't count (`cover: 5`, `cover: ""`, plain text) is treated as absent and falls back to `banner`, exactly like a null `cover`, and the focal and height keys are then `banner`'s (`banner_x`, `banner_y`, `banner_height`). With `coverProperty` set there is no fallback: a value there that doesn't count gives no banner.
  - The title is escaped as HTML text (`&` and `<`, `escapeTitleText`, the same escape as the `vault-page-title` heading).
  - Each focal axis (`<base>_x`, `<base>_y`, `bannerPosition`), trimmed, must be one keyword (`left`, `center`, `right`, `top`, `bottom`, any case), a finite number, or a numeric string (an optional `+`/`-` sign, digits with an optional decimal part) alone, with `%` or with a simple length unit (`px`, `em`, `rem`, `ex`, `ch`, `cm`, `mm`, `in`, `pt`, `pc`, `q`, `vw`, `vh`, `vmin`, `vmax`, `vi`, `vb`, `svw`, `svh`, `lvw`, `lvh`, `dvw`, `dvh`, `lh`, `rlh`, any case). Anything else is `center` for x and `50%` for y.
  - The height key is picked as before (the first non-null of `<base>_height` and the legacy `banner_height`) and only its value is checked (`bannerHeight`): a positive finite number, as a number or as a numeric string, trimmed (digits with an optional decimal part, such as `300`, `300.5` or `.5`; no sign, unit or exponent). Anything else is 500.
  - The cover URL goes through `encodeURI`, and then `'`, `(`, `)` and `&` are percent-encoded too (`bannerImageUrl`), so it can't leave the CSS string or the `style` attribute (an entity such as `&#39;` would turn into `'` inside the attribute). The image route decodes the path, so it finds the same file, and the link preview and the banner lightbox (`BG_URL_RE`, which stops at the first `)`) now read the whole URL of a file name with parentheses. A lone surrogate becomes U+FFFD first: `encodeURI` would throw and fail the whole vault's build. `#` and `?` in a cover file name still break its URL (a separate, older problem).
  - A legitimate banner (title without `&` or `<`, valid position and height, URL without those characters) comes out byte for byte as before; the only change to a valid value is the trim of a position or height with spaces around it.
  - When the body starts with an `<h1>` matching the title, only its `id` moves into the banner heading (already attribute-escaped by rehype, and inserted with a replacer function, so a `$&` or `$'` in it stays literal); the heading text is always the escaped title.
- **`properties.ts`** turns the frontmatter into `PageMeta.properties: PageProperty[]` (`buildPageProperties`): one row per visible key, in frontmatter order, `{ key, type, value, html, locked?, mismatch?, select?, colors? }`. The viewer renders the block from these rows; the page HTML only carries the marker.
  - **Type** (`builder/property-types.ts`), first match wins: the vault's `.obsidian/types.json` (Obsidian's own file), then inference from the value (boolean → `checkbox`, finite number → `number`, list → `multitext`, a date → `date`, a date with a time → `datetime`, anything else → `text`). A key named `tags` or `aliases` (any case) is `tags`/`aliases` unless `types.json` says otherwise. A key is looked up exactly first, then case-insensitively.
  - **Config files.** `.vaultwright/properties.json` at the vault root (`{ "version": 1, "properties": { "<key>": { "readonly": true, "select": ["todo", "done"], "colors": { "done": "green" } } } }`; only version 1 is read) holds settings per key: `readonly` marks it read-only, `select` makes it a single select and `colors` picks the chip color of some of its values (see Single select and Chosen colors below). Both files are optional: a missing one is silent, and an unreadable or malformed one is ignored with a warning and never fails the build.
    - Inside a readable file, an invalid entry is dropped with a warning (`.vaultwright/properties.json: "<key>": <reason>; ignorado`) and the rest still counts; `parseVaultwrightProperties` never throws. A `select` that isn't a list of strings is dropped whole; its items are trimmed, and an empty or repeated one is dropped (the first stays); `select: []` is valid. `colors` must be an object; its value names are trimmed, and a pair with an empty name, a color that is neither one of the 9 of `PROPERTY_COLORS` nor `default`, or a repeated name is dropped; a `colors` left empty counts as absent. Settings that aren't an object are ignored silently.
    - A key of the file matches a note's key exactly first, then case-insensitively, for `readonly`, `select` and `colors` alike. Everything is kept in `Map`s, so `__proto__` and `constructor` are ordinary keys, options and value names.
  - **Value**, normalized to the type: `text` → string (a number, a boolean or a date fits and becomes a string), `number` → number, `checkbox` → boolean, `date` → `YYYY-MM-DD`, `datetime` → `YYYY-MM-DDTHH:mm` (from a string with `T` or a space), list types (`multitext`, `tags`, `aliases`) → `string[]`, items trimmed and empty items dropped. Empty (absent value, blank string, `[]`) → `null`, or `[]` for a list type. A value that doesn't fit its type (`"12"` in a `number`, a loose `tags: foo`, a non-empty list in a `text`) gets `mismatch: true`, keeps the value normalized to its inferred type (a JSON-safe copy when not even that fits) and is shown as that inferred type. An unquoted YAML date is parsed by js-yaml, which rolls an invalid one over (`2024-02-30` becomes March 1st), so only a quoted invalid date in a key declared as `date`/`datetime` gives a mismatch (with no declared type it is inferred as `text`). A vault image path that `encodeURI` rejects (a lone surrogate) is shown as escaped text instead of a thumbnail, so it can't fail the build.
  - **Locks** (`locked`), in this priority: `readonly` (from `.vaultwright`); `object`, for a nested map or a list holding a map or a list (the value is a JSON-safe copy, shown as JSON); `image`, when the value cites a vault image. A locked row is meant to stay read-only, and the values index skips it.
  - **Hidden keys:** `cover`, `cover_y`, `banner`, `banner_height`, `cssclasses`, `notion-id`, `tab_label` and `note_type` on every note (any case); `parent` and `order` (exact names) only on a child note (`note_type` tab or comment, resolved or not). Every other key shows, empty ones included.
  - **HTML** (`html`) is fully escaped. The key is not in it (the viewer renders the key as text). Wikilinks in a value go through `LinkResolver.replaceWikilinksEscaped`, which escapes the text, the display, the href and an invalid link's original text; the note body still uses the raw `replaceWikilinks`. Display follows Obsidian: a value that is, as a whole, an `http(s)` URL is an external link (checked before image detection, so a URL ending in `.png` is not taken for a vault image); a vault image (`[[img.png]]`, or a bare path ending in an image extension) is a thumbnail `img.vault-prop-thumb`, listed in `assets.json`; a checkbox is a read-only `<input type="checkbox" disabled>`; a date shows as `dd/MM/yyyy` and a datetime as `dd/MM/yyyy HH:mm`; a list item is a chip `<span class="vault-prop-chip" data-color="…">`. The chip color comes from `lib/property-color.ts` (FNV-1a over the NFC key and value, one of 9 color names), so the same key and value get the same color everywhere, unless `.vaultwright` chose one (see Chosen colors below).
  - **Single select** (`select` in `.vaultwright`): the note doesn't change; the value stays text and the type stays `text`. A row gets `select: true` only when its key has `select`, its type is `text`, it has no `mismatch` and its value is empty or a string with no line break (`\r`, `\n`, U+0085, U+2028, U+2029). In that key, a number, a checkbox, a list, a date, an object or a text with a line break gives exactly the row it gives without `select`. A lock keeps `select` (a `readonly` select is still a chip, just not editable). Its HTML is one chip of the trimmed value, rendered like a list item (an image path is a thumbnail, and the row is then locked as `image`); an empty one is `''` and shows "Empty". The options are not enforced anywhere: a value outside the list shows and saves like any other.
  - **Chosen colors** (`colors` in `.vaultwright`): for any key whose row is a select or a list (`multitext`, `tags`, `aliases`, with `mismatch` too). The row carries `colors` (an object from `Object.fromEntries`; its key order carries no meaning), so the color reaches the client with the page, with no wait for the values index. Every chip of a value of that key, in reading and in the editor, takes `chipColor(key, trimmed value, colors)`: the chosen color when the trimmed value has one (exact match, checked with `Object.hasOwn`), else `propertyColor`. Besides the 9 names, a chosen color can be `default`, fainter and more neutral than `gray` (closer to the page background in both themes); it is not in `PROPERTY_COLORS` and the hash never gives it (`CHIP_COLORS` is the 9 plus `default`).
  - The new keys come after `mismatch`, in the order `select`, `colors`, and exist only when they say something: a vault without `.vaultwright` (or without `select` and `colors`) writes the same JSON as before, so `pageVersion` doesn't change. The Property API builds its row with the same `toPageProperty` and the same config, so the row it returns equals the one the next build writes.
  - The functions are pure and shared (`buildPageProperties`, `toPageProperty`, `imageTarget`, `renderPropertyValue`, `normalizePropertyValue`, `resolvePropertyType`, `isHiddenProperty`, `collectPropertyValues`), so code that changes properties can apply the same rules.
  - The escaping covers properties only: DataviewJS blocks still run vault code at build time, and their output is still trusted.

### Viewer (`components/viewer/`)
Three panes: `SidebarPanel` (tree/search) · `ContentPanel` (page) · `GraphPanel` (local graph + ToC + backlinks, collapsible, state persisted in-memory across navigation).
- `lib/parse-html-segments.ts` splits `page.html` into `HtmlSegment[]` (extracting the banner as its own segment, splitting at `.dataview-result` placeholders, with `{ properties: true }` cutting at the Properties marker and with `{ comments: true }` at the comment marker, see the Properties block and the comment strip below); `ContentPanel` renders them and **memoizes** them so unrelated re-renders (lightbox, hover preview) don't reset native `<details>` state.

- `ContentPanel` also does plain-DOM enhancement: SPA link interception, external links → new tab, image/banner lightbox, mermaid render, the Notion-style gallery filter bar (a gallery left empty hides with its group title, or with the `<details>` group whose body is only that gallery — `lib/gallery-group.ts` — and the bar is inserted above that group, never inside it; the active filter chips are remembered per `pagePath`, so they come back when the bar is rebuilt for the same page (a `router.refresh()`) and reset on navigating to another one; an always-open Notion-style text search field, ANDed with the chips, that matches the card's visible text and every `data-props` value, never the note's content, ignoring case and accents, with all words in any order, and is remembered per page together with the chips: `lib/gallery-search.ts`; the field's focus comes back after a refresh of the same page; the bar shows with 4 or more `.dv-card`s, with props or not, and with only the search when no property fits a chip), and relabeling `[data-i18n]` nodes.
- The tab bar (`components/viewer/NoteTabs.tsx`) shows `PageMeta.tabs` at the top of the content pane, above the banner and the title, outside the memoized article segments. A plain click navigates SPA-style to the tab's own URL (`router.push`), so F5 keeps the tab; a modified or middle click is left to the browser. The active tab has `aria-current="page"`. On a tab's page the local graph and backlinks are empty (tabs aren't in the graph) and the sidebar highlights nothing.
- **Properties block** (`components/viewer/PropertiesBlock.tsx`):
  - `page.tsx` passes `properties: Array.isArray(page.properties)` to `parseHtmlSegments`, which then gives a `{ type: 'properties' }` segment at `PROPERTIES_SLOT`. That constant is a copy of `PROPERTIES_MARKER`, because the builder module pulls `node:fs`; a test keeps the two equal. The slot counts only right after `<article class="vault-content">` or right after the `</h1>` of the page title that opens there; the same string typed in a note body is never cut. A text segment that would be only `<article class="vault-content">` (a page with a banner) is left out.
  - `ContentPanel` renders the segment outside the memoized elements, keyed by vault and page, inside `articleRef`, so link clicks, the image lightbox and hover previews work in it. It is the same `<details class="vault-properties">` markup the builder used to write, closed by default, with no React state for `open`: a refresh keeps it open. Each value's HTML node is memoized by its `html` string. Without rows it renders nothing.
  - A row with no value (`null`, `[]` or `html === ''`) shows `properties.empty` ("Empty"/"Vazio") in `.vault-prop-empty`, still with its lock if it has one.
  - A locked row (`locked`: `readonly`, `object`, `image`) gets an inline-SVG lock (`.vault-prop-lock`, `role="img"`) after the key, with `title` and `aria-label` from the key `properties.locked.<reason>`; an unknown reason falls back to `properties.locked`.
  - `ContentPanel` passes `showLocks` and `edit` (`{ slug, pagePath }`) only when `page.tsx` says the user can edit (`canEditVault`, read from the database and handed to `VaultViewer` as `canEditProperties`, apart from the `PageMeta` like `displayNames`, so `pageVersion` stays the hash of the JSON on disk). A reader gets no lock and no control at all: without `edit` the block renders exactly what it rendered before, with no hidden controls either (a lock on only some rows would suggest the rest is editable).
  - **Inline editing** (`PropertyEditors.tsx`, `lib/property-edit.ts`, `lib/property-local.ts`, `lib/property-client.ts`): with `edit`, a value that can be edited is a button-like element (`.vault-prop-editable`) whose `aria-label` is "Edit {key}: {visible value}" (`properties.edit.open`); a click or Enter/Space opens the editor, except a click on a link inside the value, which navigates, and a click that ends a text selection made inside the value by that same gesture (a drag to select text); a click on a selection that was already there opens it (Chromium only clears it after the click), and Enter/Space always opens it. Without hover (`@media (hover: none)`, a touch screen) the editable value gets a dashed underline in the border color, since nothing else shows it can be edited; a reader sees nothing. It only changes the value of a key that exists, through the Property API; it never adds, removes or renames one.
    - **Editors by type:** text, number, date and datetime are a native `<input>` of the matching type (no new dependency). The number field has no `inputMode` because the iOS decimal keypad has no minus key. The mouse wheel doesn't change the focused number field (a native `wheel` listener with `{ passive: false }` calls `preventDefault`, since React registers `wheel` as passive), so scrolling over it can't become a save on blur. A checkbox saves on click and uses `aria-disabled`, not `disabled`, while saving, so keyboard focus doesn't fall to `body`. Lists (`multitext`, `tags`, `aliases`) are a multi-select: the items as chips with a ×, and a field that filters the suggestions from `GET /api/vault/[slug]/property-values?key=` (loaded when the editor opens; a failed load means no suggestions and creating still works). Arrow keys move through the options and Enter picks the active one. Without an active option, Enter picks the value that already exists equal to the typed text ignoring case and accents ("acao" picks the suggestion "Ação"; if it is already a chosen item nothing is added), so it doesn't create a near-duplicate that every editor would then be offered; it never takes the first option ("RPG" is not "RPG Tático"). Creating the unaccented value is through the arrow keys, on the "Create" option. The menu shows at most 50 suggestions (`MAX_SUGGESTIONS`) besides "Create", the one equal to the typed text (by raw text or name, ignoring case and accents) first, so the cap can't hide it; past that, a dimmed row "{n} more: type to narrow down" (`properties.edit.more`) comes before "Create", and it is not an option: the arrow keys skip it and it can't be picked. The combobox carries `aria-controls` only while the menu is open. An item longer than 10,000 characters is refused when it is added, not only on saving: no chip, the text stays in the field, and the "too large" alert shows inside the editor until the text changes. The chip colors come from `chipColor` (the chosen color of `.vaultwright`, else `propertyColor`). The menu options are chips in the color they will have (`chipColor`), and the "Create" option shows the typed text, raw, as a chip in the color it will get (even a typed `[[Nova]]`; once created, the editor chip shows its name like any other item); the "{n} more" row is dimmed and has no chip, and the active option is highlighted on the whole row (background and a bar on the left), visible over the chip. An item that is, as a whole, a wikilink shows in the editor (chips, suggestions, the `aria-label` of the ×, and the provisional row) as the text the reading view shows (`wikilinkLabel` in `lib/wikilink-label.ts`, a copy of the `LinkResolver` rule that a fuzz test keeps equal), while the stored value stays `[[...]]` and the chip color keeps coming from it. The filter finds a suggestion by its name and by its raw text, and Enter also compares by name, in this order: exact raw, exact name, normalized raw, normalized name (a chosen item whose raw text or name equals the typed text, ignoring case and accents, adds nothing). These menu rules are pure functions in `lib/property-edit.ts` (`menuEntries`, `menuModel`, `enterPick`, `MAX_SUGGESTIONS`), and the menu itself is `OptionMenu`, shared with the single select.
    - **Single select** (a `select` row): a single-choice menu of the same family (`SelectEditor`, `.vault-prop-multiselect.vault-prop-select`), with the same field, filter, arrow keys, Enter rule, 50 cap, "{n} more" row, "Create" option and colored chips, over the values index (the options in the file's order, then the used values outside them). The current value shows as a chip with a × and stays among the options, but never as "Create". Picking an option (a click, or Enter on the active one) saves at once and closes. Without an active option, Enter picks by the multi-select rule (the existing value equal to the typed text ignoring case and accents, never the first option), else the typed text, trimmed. Enter on an empty field, or picking the current value, closes without calling the API. "Create" saves the typed text; the × saves `null` (the key stays as an empty `key:` and the row shows "Empty"). It saves as text, through the text field's path (`textDraftValue('text')`, the provisional row with its one chip, the 409, the errors), and the API doesn't compare the value with the options. A text longer than 10,000 characters shows the "too large" alert inside the editor until it changes. Esc cancels, and so does a real blur (there is no draft to save, unlike the text fields); a blur caused by the window losing focus keeps it open, as in the other editors. Its combobox plumbing mirrors `ListEditor`'s, so a fix in one must be checked in the other.
    - **One editor at a time.** Enter and blur save, Esc cancels; opening another row drops a pending confirmation without saving. A value equal to the current one never calls the API: blur without a change cancels, and Enter without a change just closes (on a row with `mismatch` it goes to the confirmation instead, since there Enter is the explicit request to convert). A blur caused by the window losing focus (alt-tab, switching browser tab) keeps the editor open and saves nothing: the real blur or Enter decides when the focus comes back. Emptying a number, date or datetime field sends `null`; there is no clear button. A text too long for the API shows the "too large" error instead of being cut: the inputs have no `maxLength`, which would trim a paste silently.
    - **Not editable** (`isEditable`): a locked row (`readonly`, `object`, `image`), and a text, or a list item, with a line break (`\r`, `\n`, U+0085, U+2028, U+2029): a one-line `<input>` would flatten it and the API refuses line breaks, so that value is edited in Obsidian. A value that holds a wikilink or a URL is edited as its raw text, not as the rendered link.
    - **Mismatch:** the editor opens in the declared type, with the value converted only when nothing is lost (else empty). Saving asks for confirmation inside the row (never `confirm()`) and sends `confirm: true`; Cancel (or Esc) calls nothing.
    - **Optimistic display:** the new value shows at once as a provisional row, then as the row the API returned. `lib/property-local.ts` keeps that local row in a `Map` (never a `Record`: `constructor` and `__proto__` are possible keys) and `localWins` decides when it still counts: while saving, and afterwards only while the server shows a value the local row supersedes (`stale`); it goes away when the server catches up or shows another value, which is someone else's edit and wins. When the response arrives before any refresh the entry stays even if the server row still equals it, so a build of an earlier save (a value set and then undone) can't bring the intermediate value back; the next `properties` prunes it. A 409 shows the current row from the disk (the next editor starts from it and sends it as `expected`); any other error puts the previous value back and shows the message under the row.
    - **Type changes:** the client doesn't know whether a type is declared (`types.json`) or inferred, so it doesn't refuse an empty value beforehand. Clearing an inferred number, date or datetime, or writing a text that looks like a date, comes back as the Property API's 400 `O valor mudaria o tipo da propriedade`: the row goes back to the previous value, the row stays editable, and the message says "Clearing this value would change the property's type" when `null` was sent and "This value would change the property's type" otherwise. The 400 strings the client recognizes live in `lib/property-messages.ts`, shared with the route.
    - **Refresh:** a `router.refresh()` neither closes the editor nor loses the typed text (the open editor is state of the block, and the fields keep their own text), and a refresh that still carries the old value while a save runs doesn't bring it back. `isUserBusy` postpones the `PageWatcher` refresh while an editor is open.
    - `lib/property-client.ts` calls the API with `redirect: 'manual'`, as the comment client does: without a session cookie `proxy.ts` redirects to `/login`, and the opaque redirect counts as 401 ("session expired").
  - A `PageMeta` written before this (the `<details>` inside its HTML, no `properties`) takes the old path unchanged until the vault is rebuilt.
  - CSS is in `app/vault-content.css`: the chips (`.vault-prop-chip[data-color]`) and the block's own box (`.vault-properties-wrap`, whose vertical padding is dropped so spacing matches the old in-article block).
  - Chip palette: one background per theme, in the variables `--vault-chip-text` and `--vault-chip-<color>` under `.vault-properties` (light) and `.dark .vault-properties`; a link inside a chip inherits the chip's text color. The chosen-only `default` has its own `--vault-chip-default` in both themes, closer to the background than `gray`'s, and the selector `[data-color="default"]`.
  - The link hover preview (`buildPreview(html, { propertiesHtml })` in `lib/preview.ts`) takes the banner image, else the first vault image in the property rows in order, else the first in the page HTML (the order the old in-HTML block gave), with the `src` entity-decoded.
- **Comment strip** (`components/viewer/CommentStrip.tsx`, `lib/comment-threads.ts`, `lib/comment-client.ts`): the comments of a note, between the Properties block and the body.
  - It shows only when the vault's `comments` flag is on **and** `PageMeta.commentable` is true. `page.tsx` passes that to `parseHtmlSegments(html, { comments })` and `VaultViewer` passes `ContentPanel` its `comments` prop (threads, display names, username, admin or not) under the same condition; otherwise the marker stays in the HTML as an empty div.
  - With the flag off, the comments don't reach the browser either: `page.tsx` hands `VaultViewer` a copy of the page with `comments: []` (only when the page has `comments`). `pageVersion` is still computed on the `PageMeta` read from disk, so it equals `currentPageVersion`; hashing the emptied copy would make the open tab see a new version on every check and refresh in a loop.
  - The cut is right after the Properties marker, which is where the builder writes it; this works with `{ properties: false }` too. In a `PageMeta` written before the Properties marker existed, it is at the **first** `</details>` + marker after `<article class="vault-content">` (right after the old in-HTML block). The same string typed in a note body is never the anchor. The cut gives a `{ type: 'comments' }` segment, and `ContentPanel` renders the strip there, outside the memoized elements, keyed by vault and page: navigating resets its state, a refresh of the same page keeps it (the text being typed, "Show all").
  - It lists the 3 conversations with the latest activity (`VISIBLE_THREADS`), newest first, replies in chronological order under the principal; "Show all (N)" expands the rest. A conversation with an open field or confirmation stays visible even when a refresh pushes it out of the first 3. Each comment shows the display name and `@username`, only `@username` when the user has no display name, or the raw `author` when the username is unknown to the database (`authorLabel`); the date in the browser's local time; "(edited)" when it has `updatedAt`.
  - Buttons follow the API rules, as a convenience only (the API is what enforces them): "Reply" only on a principal; "Edit" only for the author (exact username); "Delete" for the author or an admin. Deleting asks for confirmation inside the strip, never with `confirm()`, and says how many replies go with it. One action is open at a time.
  - **Shown at once, no duplicate:** the strip keeps what the API answered in local state (`LocalComments`: added, edited, deleted) and `mergeThreads` lays it over `PageMeta.comments`. An added comment the server already lists is not added again. A local edit wins only while the server copy is still the one that was edited (`commentVersion` equal to the base) or is older; otherwise the server wins. A local delete hides the comment and its replies. When a new `PageMeta` arrives, `pruneLocal` drops the local entries the server has caught up with, so a comment someone else deletes later doesn't come back. `sortThreads` repeats the builder's ordering on the merged list (a test keeps the two equal).
  - A comment's HTML node is memoized by its `html` string, so a refresh doesn't reapply it (no flicker). Links in a comment go through `ContentPanel`'s click handler like the note's (internal: SPA navigation; external: new tab). Hovering an external link inside `.vault-comments` shows no link preview: the preview would make the reader's browser load an image from a host the comment's author chose, which leaks the reader's IP. Internal links (`/vault/...`) keep their preview, and external links in the note body keep theirs.
  - Mermaid is never run on a comment: `ContentPanel` skips `pre > code.language-mermaid` inside `.vault-comments` (the text comes from a user and mermaid runs with `securityLevel: 'loose'`; the node also belongs to React).
  - Dates are formatted only after hydration (`useSyncExternalStore`), since the server doesn't know the browser's time zone; the `<time datetime>` carries the ISO value from the start.
  - `lib/comment-client.ts` calls the comment API with `redirect: 'manual'`: without a session cookie `proxy.ts` redirects `/api/vault/*` to `/login`, and following that would read the login page as a successful answer. An opaque redirect counts as 401 ("session expired"). Errors map to a short translated message by status; a 409 on edit stores the comment returned by the API as the new base and keeps the typed text, so saving again sends the new version. A 404 on delete counts as deleted.
  - The body limit (10,000 characters after normalizing line breaks and trimming, `normalizeDraft`) is checked before sending, with the same rule as the API.
  - CSS is in `app/vault-content.css` under `.vault-comments`. Headings inside a comment body are capped at the text size, so a `# title` in a comment doesn't compete with the note's headings.
- A note's `cssclasses` (list or space/comma string, `lib/css-classes.ts`) become classes on every `.vault-article`, as in Obsidian. Its width is `max-width: var(--file-line-width, 72ch)`, so a cssclass that sets `--file-line-width: 100%` in page CSS widens the page; `wide-page` still does too.
- Vault CSS written for Obsidian (a DataviewJS `view.css`, a gallery script's `<style>`) works because `app/globals.css` aliases Obsidian's variable names (`--background-secondary`, `--background-modifier-border`, `--text-normal`, `--interactive-accent`, `--font-ui-small`, …) to the viewer theme, and `ContentPanel` mirrors the next-themes theme onto `body.theme-dark` / `body.theme-light`.
- cytoscape graphs (`GraphCanvas`, `GlobalGraph`) cannot use CSS variables — colors are resolved at runtime via `getComputedStyle`.

### Auth, data, config
- Auth: JWT (`jose`) in the `vault_session` cookie, bcrypt passwords, `better-sqlite3` at `users.db` (schema auto-created in `lib/db.ts`). Users have admin/user roles; non-admins get per-vault permissions (`vault_permissions`), each at the `reader` or `editor` level (see Per-vault level below); admins see all.
- `users.display_name` (TEXT, `NULL` = no name) is an optional display name the admin edits; comments show it before `@username`. `lib/display-name.ts` validates it: trimmed, empty becomes `null`, at most 80 characters, no control characters. `applySchema` adds the column with `ALTER TABLE users ADD COLUMN display_name TEXT`, guarded by `PRAGMA table_info(users)`, so it is idempotent and an existing `users.db` is migrated the first time it is opened, with no separate migration step.
- **Per-vault level.** Each grant in `vault_permissions` has a `level`: `reader` (sees the vault) or `editor` (may also change it; for now that is the property values of its notes, through the Property API below, the two routes that use `editorSession`). The column is `level TEXT NOT NULL DEFAULT 'reader' CHECK (level IN ('reader','editor'))`, a CHECK because SQLite has no ENUM. `applySchema` adds it to an existing `users.db` the first time it is opened, guarded by `PRAGMA table_info(vault_permissions)` like `display_name`, so grants that already existed become `reader`. Admins need no grant: they see every vault and count as editors in every one. In `lib/db.ts`, `dbUserHasVaultAccess` and `dbGetUserPermissions` (slugs) still answer read access, at any level; `dbGetUserVaultLevel(userId, slug)` gives the level (`null` = no access); `dbGetUserVaultPermissions` lists `{ slug, level }`; `dbSetUserPermissions(userId, [{ slug, level }])` replaces all of a user's grants in one transaction, and a repeated slug or a level outside the CHECK throws with nothing changed. `VAULT_LEVELS` and `isVaultLevel` (exact match, no trim or case folding) live in `lib/vault-level.ts` so the client can use them.
- **Vault sessions** (`lib/vault-session.ts`). `vaultSession(slug)` is the check shared by the routes that write inside a vault (the comment API, and the Property API, both its PATCH and its values read, through `editorSession`), in this order: session cookie and `verifyToken` (401); the user still exists in the database (401); access to the vault, admin or a grant at any level (403); the vault exists (404). `editorSession(slug)` adds one step: `editor` level or admin (403). That rule is `canEditVault(userId, slug)` (the user's row exists and the user is an admin or has the `editor` level, read from the database); `page.tsx` uses it too, to decide whether the viewer gets the property editors. `commentSession` is `vaultSession` plus the `comments` flag. Username, admin role and level are read from the database on every call, never from the JWT, so demoting a user, removing a grant or deleting the user takes effect on the next request while the token is still valid. The read paths (`preview`, `page-status`, `page-version`, the image route, `proxy.ts`, and the vault list of `/api/vaults` and the home page via `getVisibleVaults`), `requireAdmin` (the admin routes) and the page guards don't use it: they still read `isAdmin` from the JWT and don't check that the user still exists (a deleted non-admin has no grants left, so only a deleted admin's token still reads until it expires).
- **Admin permissions API.** `PUT /api/admin/users/[id]/permissions` takes `{ vaults: [{ slug, level }] }` and validates every item before writing anything: `vaults` not an array (the old `{ vaultSlugs }` shape included) → 400; an item that isn't an object with a text `slug` → 400; a `level` that isn't exactly `reader` or `editor` (missing, `Editor`, `admin`) → 400; a repeated slug → 400. Then slugs not in `vaults.config.json` are dropped and the rest replaces the user's grants; the answer is `{ success: true, vaults }` with what was saved. `GET /api/admin/users` and the admin page give each user `vaults: [{ slug, level }]` (`UserPublic.vaults`). In the admin panel each vault has a three-way control (no access, reader, editor), the users table marks the vaults where a user is an editor, and Save checks the permissions PUT and shows its error. When a new user was created but its permissions failed, the next Save goes through that user's edit path instead of creating it again.
- **Deleting a vault** (`DELETE /api/admin/vaults/[slug]`) also deletes every grant on its slug, for every user (`dbDeleteVaultPermissions`), and only after the vault has left `vaults.config.json` (a failed config write leaves the grants alone; a failed grant delete answers 500): slugs are deterministic (`lib/slugify.ts`), so a vault recreated with the same name would otherwise inherit the old grants, `editor` ones included.
- Vault images are **not** under `public/`: the builder only lists them in `data/<slug>/assets.json`, and `app/vault-assets/[slug]/[...path]/route.ts` serves them straight from the vault folder, on the same URL the HTML carries (`/vault-assets/<slug>/<path in the vault>`). The route accepts only paths in that vault's `assets.json` (matched case-insensitively; read with an mtime-aware cache, so a new build is valid on the next request, no restart), then re-checks that the resolved file is a regular file inside the vault with an image extension. Anything else is 404. Why not `public/`: `next start` lists `public/` **once, at boot**, so an image copied afterwards answered 404 until a restart, and copying thousands of images made the build several times slower and duplicated gigabytes.
  - Auth is in two places on purpose: `proxy.ts` checks first (session; for readers, permission on the vault via `lib/asset-guard.ts`, on the decoded path with a case-insensitive `/vault-assets/` prefix — the host filesystem is case-insensitive — and the slug as written, since grants hold the configured slug), and **the route checks again** (401 without a session; 404 for a reader without permission, so "no access" can't be told from "doesn't exist"). The proxy is no longer the only gate. **The proxy matcher must not exclude images or `vault-assets`**: until 2026-11-13 it did, and every vault's images were public.
  - The handler reads the whole file and has its own `HEAD`: Next derives `HEAD` from `GET` and discards the body without cancelling the stream, which leaked a file descriptor per request. Headers: `Cache-Control: private, no-cache` (the browser revalidates with `ETag`/`Last-Modified`; a shared cache must not keep an image that needs a session), `X-Content-Type-Options: nosniff`, and for SVG a restrictive `Content-Security-Policy` so an SVG opened in its own tab can't run script on the viewer's origin.
  - Consequences of listing only what pages cite: if the vault's disk is offline its images disappear while the pages stay, and a renamed image is 404 until the next build.
  - **Deploy:** delete the old `public/vault-assets/` **before** the server starts. If it exists at boot, the old copies enter Next's list and are served ahead of the route, ignoring `assets.json` and its permission check. Order: run the new builder on all vaults (`--all`; the old server keeps serving the old copies, same URLs), `npm run build`, delete `public/vault-assets/`, restart. Images answer 404 for a few seconds between the last two steps.
  - `images.unoptimized` keeps `/_next/image` (unused) from serving them by another route.
- `better-sqlite3` ≥ 13 is N-API, so its binary survives Node upgrades; 12.x was tied to one Node ABI and broke login (HTTP 500) when the host's Node changed. Its install script is denied in `allowScripts` on purpose: the package ships prebuilt binaries, and the script would only recompile from source.
- Build state (`getBuildState`, the queue behind `runRebuild`) lives in an object on `globalThis` under `Symbol.for('vault-viewer.rebuild')`, not in a module variable. Turbopack runs **pages** and **route handlers** in two separate runtimes (`chunks/ssr/[turbopack]_runtime.js` vs `chunks/[turbopack]_runtime.js`), each with its own `moduleCache`: a page importing `lib/rebuild.ts` would get another module instance, would not see a build started by the internal route, and could run a second build of the same vault at once. Per vault it holds `running` (with `startedAt`), `queued`, the `first` paths of the queued build, and `lastAttemptStartedAt` (start of the last build that ended, **successful or not**). `runRebuild(slug, { first })` passes each `--first` as its own spawn argument; a request joined to a running build puts its `first` into the extra build.
- **Pending pages** (`lib/pending-page.ts`): content newer than the last build must not be a 404 or a silently stale page. For a page path `p` (the decoded URL path for a page that doesn't exist; `page.path` for one that does; synthetic folder pages are out; a path inside the root `_comments/`, in any case and at any depth, is never a page, so opening the URL of a comment file is a 404 with no build), the page is pending when: `p` is safe (no `..`, `\`, empty or dot-leading segment, none of the characters Windows rejects); `<p>.md` or `<p>.canvas` exists in the vault and the scanner would visit it (`isScannedPath`, the same `.viewerignore` predicate); and `t = noteTime(stat)` is newer than what a build has seen. A running build that started after `t`, or a queued one, only has to be waited for. Otherwise, if `t > lastScan`, the page **requests a build** with `first: [p]` (fire-and-forget). `lastScan = max(index.json.startedAt ?? builtAt, lastAttemptStartedAt)`; the second term is what stops a loop: a note the builder can't generate, or a build that fails, costs **one** build and then falls to 404 (or to the page as it is). Within the pending rule, only the page triggers builds (the internal rebuild route, the admin and the comment API also do, for their own reasons). `GET /api/vault/[slug]/page-status?path=<p>` (same auth as `preview`, `Cache-Control: no-store`, `{ state: 'ready' | 'pending' | 'missing' }`) only reads, and treats a page JSON that doesn't parse (read mid-write) as absent, never `ready`. A page JSON newer than `t` is already the new version and skips the rule.
  - Windows path aliases bypass a textual `.viewerignore` check: NTFS stream syntax (`Name::$INDEX_ALLOCATION`), 8.3 short names, trailing dot or space, and folder links. So `noteFor` also requires the **canonical** path (`realpath`) of the file to equal `<p>.md`/`.canvas` case-insensitively. This matches `walkVault`, which doesn't follow folder links.
  - UI (`app/(app)/vault/[slug]/[[...path]]/page.tsx` + `components/viewer/PageStatusNotice.tsx`): a missing-but-pending page renders the normal viewer with a provisional page ("this page is being generated…"); an existing-but-stale one renders as is with an "updating this page…" strip. `PageStatusNotice` polls the status route (every 1 s for the first 30 s, then every 5 s, giving up after 5 min, the same value as `REBUILD_TIMEOUT_MS` but its own constant, `POLL_GIVE_UP_MS`) and calls `router.refresh()` on `ready` or `missing`. The refresh is capped (at least 5 s between two, at most 3 per mount; `lib/page-status-poll.ts`) so a status that never settles can't refresh forever. Open `<details>` may reset on the refresh; the refresh is expected to keep the scroll position. On giving up, the wait screen shows "reload later", while the "updating…" strip just disappears without a message.
- **Open tab refreshes itself** (`lib/page-version.ts`, `lib/page-watch.ts`, `components/viewer/PageWatcher.tsx`): when a rebuild changes the page a tab shows, the tab calls `router.refresh()` on its own. The version of a page is the sha1 of the `JSON.stringify` of its `PageMeta` (`pageVersion`), which `page.tsx` computes on the very object it renders; the file mtime is not usable because the builder rewrites every page JSON on every build, changed or not. `GET /api/vault/[slug]/page-version?path=<p>` (same auth as `page-status`, `no-store`) answers `{ version: string | null, building: boolean }` from disk (`currentPageVersion`, cached by mtime and size; `null` for an unsafe path, a missing page or a JSON that doesn't parse; folder pages are hashed from the synthetic page). `PageWatcher` creates the watcher inside its effect (`stop()` is terminal and StrictMode runs effect, cleanup, effect) and feeds it `visibilitychange`, `focus` and the user's interactions.
  - Cadence (`createPageWatcher`): a hidden tab polls nothing; coming back (or focus) checks right away (deduped within 1 s), then waits 0.5 s, 1 s and 1.5 s between the next checks (`RETURN_RAMP_MS`, so at 0.5, 1.5 and 3 s), then every 2 s until 20 s after the return; each return restarts the ramp; while a build is running or a newer version is waiting, every 2 s (the build part capped at 5 min); otherwise every 60 s.
  - Refresh only when the version differs from the rendered one, and never twice in a row for the same version (it only remembers the version it last refreshed for, so content that goes back to an older version later still refreshes), no more than once every 5 s. It is postponed while the user is busy: the filter menu (`.dv-filter-menu.is-open`) is open, a property is being edited (`.vault-properties .vault-prop.is-editing`, even with no recent interaction: the refresh would close the editor and lose what was typed), or focus is in an editable field (text-like `input`, `textarea`, `select`, `contenteditable`) with an interaction in the last 3 s (`isUserBusy`). A failed check (network, non-ok, a body of the wrong shape, or no answer within a 10 s fetch timeout) counts as no news: it changes nothing and doesn't refresh. `building` means a build running or queued in this server process (`getBuildState`); a build run from the CLI (`npx tsx builder/index.ts`) isn't seen as building, so an open tab picks it up on its next check (on return to the tab, or within 60 s while visible).
  - Refreshing without a change is avoided on purpose: React 19 reapplies `innerHTML` for every new `page` object, so a refresh with identical content would make the page flicker.
  - A pending page (generating or updating) is left to `PageStatusNotice` and isn't watched, and neither is a page while the global graph is open (a refresh would rebuild the graph and lose zoom and position; the watcher remounts and checks right away when it closes). A note that disappeared gets no refresh (`version: null` is never "news").
- Builds run through `lib/rebuild.ts` (`runRebuild`): the builder is spawned as `process.execPath --import tsx builder/index.ts`, without a shell (`spawn(cmd, args, { shell: true })` is deprecated, DEP0190), one build at a time per vault; requests arriving during a build coalesce into ONE extra build (`wait: true`, used by the admin route and by the internal route with `?wait=1`, resolves with that extra build's result). A build that throws (its promise rejects instead of settling through the child's events or the timer) counts as a failed build, handled exactly like one that exits non-zero: its result is `ok: false` with the error message as `output`, `lastAttemptStartedAt` is recorded and the lock is released (or the next extra build starts), so a failing build never makes `runRebuild` reject.
- `POST /api/internal/rebuild/<slug>` (header `X-Rebuild-Key` = `INTERNAL_REBUILD_KEY`) lets the external sync service trigger a rebuild. `proxy.ts` lets `/api/internal/` through without a session, so the route authenticates itself, in this order: `cf-connecting-ip`/`forwarded`/`x-real-ip` present, or `x-forwarded-for` with a non-loopback IP (Next injects it with the socket address on every request, so its mere presence proves nothing) → 403; `Host` not loopback (`127.0.0.1`, `localhost`, `[::1]`, any port) → 403; env var unset → 404; wrong/missing key → 401 (SHA-256 digests + `timingSafeEqual`); invalid slug → 400; vault not in `vaults.config.json` → 404; else 202 without waiting for the build. With `?wait=1` (exactly `1`; no parameter or any other value keeps the 202), it answers only when the build that covers the request ends, i.e. `runRebuild(slug, { wait: true })`: with a build already running, that is the extra build queued after it. 200 `{ ok: true }` if that build succeeded, 500 `{ ok: false }` if it failed or hit `REBUILD_TIMEOUT_MS`; the build output goes to the log, never to the body. A client that gives up and disconnects (the sync service waits 15 s after creating or resyncing a note) cancels nothing: the build runs to the end and its result is dropped. The no-wait 202 is what the sync service's 60 s debounce uses, so it must not change. Security depends on: the viewer listening on loopback only; the reverse proxy forwarding the original `Host` (a `header_up Host` rewrite defeats the check); and the caller using `127.0.0.1`/`localhost`.
- `vaults.config.json` (gitignored — copy from `vaults.config.example.json`) defines vaults; read via `lib/vault-config.ts` with an **mtime-aware cache** (re-reads when the file changes, so the admin UI and routes stay consistent without a restart). Per-vault `titleProperty` / `coverProperty` / `homePage` drive the builder. Per-vault `comments` (boolean, off by default) turns comments on for that vault. The builder ignores it; the viewer and the API apply it at request time. When it is off, `page.tsx` empties `comments` only in what it sends to the client, never in the `PageMeta` it hashes (see Comment strip).
- **Display names at request time** (`lib/comment-authors.ts`):
  - When the vault's `comments` flag is on and the page is commentable, `page.tsx` resolves the comment authors and the logged-in user to display names (`dbGetDisplayNames`).
  - It passes the map as the `displayNames` prop of `VaultViewer`, **outside** the `PageMeta`. `pageVersion(page)` must hash exactly the JSON on disk, as `currentPageVersion` does; names inside the `PageMeta` would make every check see a new version, and the open tab would refresh in a loop.
  - A username missing from the map is unknown to the database; `null` means a user without a display name.
- **Comment API** (`app/api/vault/[slug]/comments/route.ts`, `lib/comment-api.ts`, `lib/comment-store.ts`): one of the two places where the viewer **writes to the vault** (the other is the Property API below, which writes into a note's own file), and it writes only inside `<vault>/_comments/`. The pieces any write into the vault needs (atomic replace with retry while Windows holds the file, the per-vault write queue, the link resolver of the build) live in `lib/vault-write.ts`.
  - `POST { parent, body }` creates a comment. `parent` is the path of a note or of a comment, and the server finds out which: a note makes a principal comment; a comment makes a reply, and replying to a reply stores the `parent` of the conversation's principal (one level). Answer: 201 `{ comment: PageComment, replyTo }`, `replyTo` being the principal's path or `null`. The parent comment may live anywhere in the vault (it is only read); the new file always goes to `_comments/<mother path>/`.
  - `PATCH { path, body, version }` edits the body. Answer: 200 `{ comment }`, or 409 `{ error, comment }` (the current comment) when the file changed since the client read it. `version` is `commentVersion(comment)` (`lib/comment-version.ts`), a pure function of the `PageComment` the client holds (`body`, `createdAt`, `updatedAt`), so the build stores no version and a body changed by hand in Obsidian is caught too. It is a non-cryptographic hash because it has to run the same in the browser; it protects nothing.
  - `DELETE { path }` removes the file for good. Answer: 200 `{ deleted }`, the number of files removed, the comment itself included. Deleting a principal also deletes its replies, i.e. every comment **inside `_comments/`** whose `parent` chain climbs to it; a hand-written reply outside `_comments/` is left alone and becomes an orphan. Deleting a reply deletes only that file. Replies are removed before the principal, and folders left empty under `_comments/` are removed.
  - Who can do what, checked in this order (`commentSession`, whose first four steps are `vaultSession`): session cookie and `verifyToken` (401); **the user still exists in the database** (401; a deleted user's JWT is valid for 7 days); access to the vault, admin or a grant at any level (403); the vault exists (404); the vault's `comments` flag is on (403). Username and role come from the database row, not from the token. Then: anyone who got this far creates and replies; only the author edits (an admin doesn't); the author or an admin deletes. "Author" is the frontmatter `author` equal to the username, exactly (no trim, so `ana` is not the author of what `" ana"` wrote; usernames themselves are not validated on creation).
  - The request must be `Content-Type: application/json` (415 otherwise) with an object body, at most 128 KB (413); `DELETE` carries a JSON body too. There is no CSRF token: the cookie is `sameSite: lax` and another site can't send JSON without a preflight. The body is required and at most 10,000 characters, counted after normalizing line breaks to `\n` and trimming (the builder reads it trimmed). A body past the nesting limit (`commentTooDeep`, see the restricted render) is 400 `{ error: 'O comentário tem aninhamento demais' }` on POST and PATCH, checked after the session and the JSON body, with nothing written. `createComment` and `editComment` also render the new body before they create a folder or write a file, so a render that throws is a 500 with the disk untouched and no build requested. `proxy.ts` still redirects `/api/vault/*` without a cookie to `/login`; the route checks the session itself.
  - Paths from the client go through `safePagePath` and the canonical check (`scannedVaultFile`, the `realpath` rule of pending pages); the extension must be a lowercase `.md`, as the scanner requires. The mother must exist in the build with `commentable: true` (a note created after the last build is refused until it is built) and on disk. The target of an edit or a delete must be a comment (`note_type: comment` with a text `parent`) inside `_comments/`: a file there that is not one (unreadable frontmatter, another `note_type`) is 404 on delete and 422 on edit, never rewritten. The API reads frontmatter with the builder's YAML-only rule (`parseYamlFrontmatter`, see Builder pipeline), so a frontmatter in any other engine counts as unreadable, and so does one that is not a map (a YAML scalar or list). An existing segment of the destination folder must be a plain directory (`lstat`), so a link or junction can't take the write out of the vault. If `.viewerignore` hides `_comments/`, creating answers 409: the build would never show the comment.
  - File name: `<YYYY-MM-DD HHmmss> <username>-<4 chars of [a-z0-9]>.md`, in the server's local time. The username loses the characters a file name can't hold (the frontmatter `author` keeps the original). On a name collision the suffix is drawn again, up to 10 times.
  - The frontmatter is always generated by the server (`serializeComment`): `note_type`, `parent`, `author`, `created_at` and, after the first edit, `updated_at`. Text values are written as JSON strings, which YAML reads as double-quoted scalars, so an `author` or `parent` with `: ` or a line break can't break the YAML; dates are unquoted ISO 8601 with the server's offset. `parent` is written with brackets when `parentRef` reads the same path back and bare otherwise (a `#` or `]` in a note name). An edit goes through the same serializer and keeps what it doesn't own: `parent` as written, `author`, and every extra hand-written key (dumped by gray-matter's YAML engine); only `updated_at` and the body change, and `created_at` is rewritten in the server's offset (same instant).
  - A new file appears under its final name already complete and never overwrites: the content goes to a temporary file in the same folder (dot-leading, `.tmp`, so neither the scanner nor Obsidian takes it for a note) and the final name is created with `link`, which is atomic and fails if the name exists. On a disk without hard links (exFAT, some shares) it falls back to reserving the name with `wx` and renaming the temporary file over it; the final name is empty for an instant, and the builder ignores an empty file in `_comments/`. An edit is temporary file + `rename`, retried while Windows holds the file (`EPERM`/`EBUSY`/`EACCES`, about 300 ms in total).
  - Writes of one vault run one at a time (a promise queue per slug on `globalThis`, `Symbol.for('vault-viewer.comment-locks')`), so the "check the version, then write" of an edit and the cascade of a delete can't interleave with another write in this process. A change made outside the server (Obsidian, an agent) in that window is not covered.
  - The returned `PageComment` is built by reading the file back through `toPageComment`, with a `LinkResolver` over the same set the build uses (scanned notes plus canvases outside `_comments/`), so it equals what the build writes next. This scans the vault on each write.
  - **Silent rebuild:** after each write the route calls `runRebuild(slug, { first: [mother] })` without waiting (`first` is empty when the comment has no mother, e.g. an orphan being deleted). Requests in a row coalesce into one build. An error that comes after the disk already changed (a cascade that stops halfway, a read-back that fails after the write) still asks for the build, so the page doesn't stay stale behind a 500. The client shows the returned comment at once; other tabs and other people get it after the build, through the tab that refreshes itself.
- **Property API** (`app/api/vault/[slug]/properties/route.ts`, `lib/property-api.ts`, `lib/property-store.ts`, `lib/frontmatter-edit.ts`): changes the value of a property that already exists in a note, writing into the note's own `.md`. It never adds, removes or renames a key.
  - `PATCH { path, key, value, expected, confirm? }`: `path` is the note path without `.md`; `key` the exact frontmatter key (a string of 1 to 1,000 characters); `value` the new value; `expected` the value the client saw (the row's `value`); `confirm`, when present, a boolean. `value` and `expected` are required, `null` included (checked with `Object.hasOwn`). Answer: 200 `{ property: PageProperty }`, the row as the next build writes it. An error is `{ error }` with a pt-BR message, and a 409 also carries `property`, the current row on disk.
  - Checked in this order: `editorSession` (no cookie or a bad token 401; the user no longer in the database 401; no access to the vault 403; the vault doesn't exist 404; not an editor 403); the JSON body (`readJsonObject`: 415, 413, 400, as in the comment API); the fields (400); then, inside the per-vault write queue shared with comments (`withVaultLock`): the path as text (400, or 404 inside `_comments/`), the vault's property config (503), the path on disk (404), the note in the build (404 or 422), the file (404, or 422 when it isn't valid UTF-8), the frontmatter, the key, a hidden key and a locked row (422), `expected` and `confirm` (409), the value (400, or 409 when the build's type for the key is not the one on disk), a value citing an image (400), the rewrite (422), a change of type (400) and the write itself (409 once the note keeps changing).
  - Who: an editor of the vault (a grant at the `editor` level) or an admin; a reader gets 403. Username, role and level come from the database on every request.
  - **Trust boundary:** the `editor` level is as trusted as someone who writes the vault's files on disk. The row the API returns is escaped, and so is the banner the rebuild writes: the `titleProperty` title in its heading, the position and height keys `<base>_x`, `<base>_y` and `<base>_height` in its `style`, and the cover key of a vault's own `coverProperty` in its `url()` (see `banners.ts` above). Dataview output still trusts the frontmatter: the rebuild hands it the saved value unescaped (table cells and list items, and `file.link`, which the viewer inserts as HTML). So an editor can still put markup and script into pages that every reader of the vault opens, admins included, through any DQL or DataviewJS block that shows a key they can edit. Grant `editor` only to someone already trusted to that degree. Hardening Dataview's output is a separate decision, and DataviewJS keeps trusting the vault's content.
  - Keys that can't be edited are 422 for everyone, admins included (it is a property of the key, not a missing permission): a hidden key (`isHiddenProperty`, with `parent` and `order` hidden only on a child note) and a locked row (`readonly`, `object`, `image`). The key must exist in the frontmatter **on disk** (not in the build's JSON), else 422.
  - Paths: `safePagePath` (400) and the canonical check (`scannedVaultFile`, the `realpath` rule of pending pages), so a Windows path alias, a junction or a link can't make the write reach another file, inside or outside the vault; the extension must be a lowercase `.md`, and a note hidden by `.viewerignore` is 404. Anything inside the root `_comments/` (any case, any depth) is 404: a comment is not a page. A path in another case is accepted and writes the canonical file, and the log and the rebuild use the canonical path.
  - The note must be in the build: `data/<slug>/pages/<note>.json` readable (404 otherwise, so a note created after the last build is refused until it is built) and with `properties` as an array (422 otherwise).
  - The row being edited is `toPageProperty(key, frontmatter[key], ctx)` over the file on disk, with a context equal to the build's: the same `LinkResolver` (`vaultLinkResolver`), the same image index (`scanImages` + `ImageHandler`) and the property config. The config is read once per request, before the note is touched, by `readPropertyConfig` (`lib/property-store.ts`) with the build's parsers (`parseObsidianTypes`, `parseVaultwrightProperties`): a missing file (`ENOENT`) counts as absent and a malformed one is ignored with the build's warning, as in the build; any other read error (a folder in its place, a permission, a lock that persists) is 503 `A configuração de propriedades do vault não pôde ser lida`, with nothing written. The build's `loadPropertyConfig` is not used here because it never throws: on such an error it returns an empty config, and a `readonly` key would be editable for that moment. A file read while another program is still writing it without an atomic replace (empty or cut short) is malformed to this rule, so for that moment its `readonly` keys are editable and its declared types are gone. The resolver and the index scan the vault, so each is built only when a value needs it.
  - A single select's value is text like any other: the API returns the row with `select` and `colors` as the build does, but never checks the value against the options.
  - The value is checked against the row's `type` (`validateEditValue`, 400 with the reason): text is a string with no line break (`\r`, `\n`, U+0085, U+2028, U+2029) of at most 10,000 UTF-16 units; number a finite number; checkbox a boolean; date `YYYY-MM-DD` and datetime `YYYY-MM-DDTHH:mm`, only in the exact form the builder reads back unchanged; any of these may be `null` (clears the value, the key stays) when the type rule below allows it. A list type (`multitext`, `tags`, `aliases`) takes an array of strings (`[]` empties it, `null` is refused), items trimmed, with no empty or repeated item (exact comparison after the trim) and no line break, each at most 10,000 units. Then a text or list value that cites a vault image (a bare path ending in an image extension or an image wikilink, in the value or in any item: the builder's own rule, checked as `toPageProperty(key, value, ctx).locked === 'image'`) is 400 `O valor não pode citar imagem do vault`, since the row would become locked. A value that is, as a whole, an `http(s)` URL passes even when it ends in `.png`.
  - **An edit never changes the property's type.** The type the next build would give the written value (`resolvePropertyType` over the edited frontmatter, read back with `readFrontmatterData`) must be the row's type, else 400 `O valor mudaria o tipo da propriedade`, with nothing written. It is checked after the rewrite and before the write; the same-value shortcut doesn't reach it. So clearing an inferred number, checkbox, date or datetime is refused (an empty `key:` reads as `null`, which infers `text`), and so is giving a text a value that looks like a date (`2024-01-02`, written quoted, infers `date`). A type declared in `types.json` and the fixed `tags`/`aliases` are unaffected (clearing a `number` declared there writes `key:`), `[]` keeps a list a `multitext`, and `"true"` or `"123"` stays text.
  - `expected` different from the row's value on disk (deep JSON equality) is 409 `{ error, property }`, with nothing written. A row with `mismatch` also needs `confirm: true` (409 `{ error, property }` otherwise), and the value is then written in the row's type. Both 409s come before the value is validated: when the disk or `types.json` changed since the client read the row (`rating: 3` became `rating: três`, or a number is now declared `checkbox`), the client gets the current row, not a 400 for a value meant for the old type. When `types.json` changed the type but not the normalized value (a text `due: 2024-01-05` now declared `date`, or a `rating: "12"` whose `number` declaration was removed), neither 409 fires; then a value that fails validation is the same 409 `{ error, property }` with the current row, instead of the 400, whenever the row's type in the build's JSON differs from its type on disk. Only a validation failure gets there, so a value valid for the new type is written and there is no loop until the rebuild; once the build and the disk agree, an invalid value is the 400 again.
  - The same value as on disk, without a mismatch: 200 with the current row, with no write, no rebuild and no log line.
  - **Write format** (`editFrontmatterValue`): text as a JSON string (`yamlString`, which YAML reads as a double-quoted scalar, so `"123"` and `"true"` stay text; DEL and the C1 controls (U+007F–U+009F), U+2028, U+2029 and U+FEFF are escaped as `\uXXXX`); text that is only whitespace, and `null`, as an empty `key:`; a number as `String(n)`; a checkbox as `true`/`false`; date and datetime unquoted; a list as `key:` followed by one `  - "item"` line per item, and an empty list as `key: []`. The key line keeps the file's text from column 0 up to and including the separating `:`. New lines take the line break of the opening `---` line (`\r\n` when it ends that way, else `\n`).
  - **Only that key's block changes**: from the key line up to the next column-0 key line or the closing `---`, minus the blank lines and column-0 `#` comments at its end, which stay. A comment at the end of the key line and an indented comment inside the block go away with the old value, and so does a column-0 `#` comment between two lines of the block; only the ones at the end of the block stay. Everything else (the other keys, comments, order, quoting, CRLF, BOM and the body) stays byte for byte. The file is decoded with `TextDecoder('utf-8', { fatal: true, ignoreBOM: true })`, so a BOM is written back as it was.
  - When `lib/frontmatter-edit.ts` can't guarantee that, it refuses (422) rather than rewrite "as best it can": no frontmatter; an unreadable one (broken YAML, another engine) or one that isn't a map; a repeated key; the key missing; an anchor or alias in the key's block; and any shape it can't rewrite safely (no closing `---`, a merge key `<<`, a flow map, a complex `?` key, a key with an anchor, tag or alias, a column-0 line that isn't a recognizable key, a quoted value still open at the end of the block, a lone `\r`). As a safety net, the new text is parsed again and must give the same keys in the same order, the same value for every other key, the new value for this one and the same body, else 422.
  - **Conflicts with other writers** (Obsidian, the sync service, an agent): each attempt reads the bytes, runs the checks above, writes the new content to a temporary file in the same folder and, right before **each** try of the `rename`, reads the note again and compares the bytes (`replaceFileIfUnchanged` in `lib/vault-write.ts`): a `rename` refused because Windows holds the file waits for the next delay and reads again (the same tries and delays as the other retries), so a change made during that wait is not overwritten. If the bytes changed or the note is gone, nothing is replaced and the attempt starts over from the path, so a change to another key is kept along with this one, and a change to the same key gives the 409 of `expected`. Up to `MAX_EDIT_ATTEMPTS` = 4 attempts (the first plus 3 redos); then 409 `A nota mudou enquanto era gravada` with the last row read. Reading the note and the `rename` are retried while Windows holds the file.
  - Each write logs `[properties] "<username>" "<slug>" "<note path>" "<key>"`, each value a JSON string with `yamlString`'s extra escapes (DEL and the C1 controls, U+2028, U+2029, U+FEFF), so nothing a user typed can break or inject a log line.
  - **Silent rebuild:** after each write the route calls `runRebuild(slug, { first: [notePath] })` without waiting; requests in a row coalesce into one build. An error that comes after the disk already changed (the read-back fails) answers 500 `Erro ao gravar a propriedade` but still logs and still asks for the build, so the page doesn't stay stale.
  - Not covered: a change made outside the server between the last byte comparison and the `rename` that succeeds is overwritten; and the `rename` recreates the file, so it gets a new `birthtime`, a hard link to it is broken (the other name keeps the old content), and it loses its mode and owner on POSIX and its explicit ACEs on Windows.
  - `GET /api/vault/[slug]/property-values?key=<key>` (`getPropertyValues` in `lib/vault.ts`): the values already used in a list property, to suggest while editing. It only reads `data/<slug>/property-values.json`. Same `editorSession` as the PATCH (a reader is 403), `Cache-Control: no-store`, 400 `{ error: 'key ausente' }` without `key`. The answer is `{ values: string[] }`; `[]` for a key with no index (checked with `Object.hasOwn`, so `__proto__` is just a key with no index) and when the file is missing or doesn't parse.
- The admin UI (`/admin`) edits users and vaults and can trigger a rebuild by spawning the builder (`app/api/admin/vaults/[slug]/rebuild`).
- `.viewerignore` (gitignore syntax) at a vault root hides files/folders from the build — applied in `builder/scanner.ts` via `builder/vault-ignore.ts`. The image route does not apply it: an image in an ignored folder cited by its full path is still served (deliberate decision).

### i18n (`lib/i18n/`)
Flat dictionaries per locale (`en.ts`, `pt-BR.ts`); add a language by copying a file and registering it in `index.ts` `LOCALES`. The active locale is resolved in `app/layout.tsx` from the `vault_locale` cookie or `Accept-Language` (fallback `en`). Client components use `useI18n().t(...)`; server components use `await getT()`. Strings the builder bakes into HTML carry a `data-i18n` attribute and are relabeled client-side, so locale switching needs no rebuild. The Properties block label is the exception now: `PropertiesBlock` is a React component and uses `t('properties.title')` directly; the `data-i18n` span only exists in pages built before the Properties marker.

## Testing
Vitest, node environment (jsdom is available for DOM-dependent tests). Tests in `tests/` mirror `builder/` and `lib/`. Builder plugins are pure functions tested directly; prefer adding a focused test next to the plugin you change.
