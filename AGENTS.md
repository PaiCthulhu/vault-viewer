## Commands

```bash
npm run dev            # Next.js dev server (http://localhost:3000)
npm run build          # production build of the web app
npm run start          # serve the production build
npm run lint           # eslint

npm test               # vitest (watch)
npm run test:run       # vitest once (CI-style)
npx vitest run tests/builder/plugins/callouts.test.ts   # a single test file
npx vitest run -t "callout"                              # tests matching a name

# Vault rendering (ahead-of-time builder — NOT part of `next build`)
npx tsx builder/index.ts --vault <slug>   # build one vault
npx tsx builder/index.ts --all            # build every vault in vaults.config.json

npx tsx scripts/seed-admin.ts <user> <pass>   # create the first admin (creates users.db)
```

After ANY change under `builder/`, rebuild **every** vault (`--all`) — build output is per-vault and goes stale silently otherwise.

## Architecture

This is **two programs** sharing one repo:

1. **The builder** (`builder/`) — an ahead-of-time renderer run from the CLI (`npx tsx builder/index.ts`). It reads an Obsidian vault folder from disk and writes prebuilt output to `data/<slug>/`. It does not copy images: it only records which ones the pages cite (`assets.json`), and a route serves them from the vault.
2. **The Next.js viewer** (`app/`, `components/`, `lib/`) — at request time it only **reads** that prebuilt `data/<slug>/` output; it does no markdown rendering. So content changes are invisible until the vault is rebuilt.

### Build output contract (`data/<slug>/`)
- `pages/<path>.json` — a `PageMeta` (final HTML + frontmatter + outlinks + per-page CSS; `tabs` only on a tab bar's mother and its tabs; `commentable` and `comments` only on a commentable page, see Comments below). A comment (see Child notes below) gets no page JSON.
- `pages-index.json` — `PageSummary[]` (path, title, **file** [basename], tags) for sidebar/search. Child notes (tabs, comments) are left out of it, of `tree.json` and of `graph.json`.
- `tree.json` — the sidebar tree, prebuilt with folder-notes already absorbed (built at build time so the client doesn't recompute 700+ nodes per navigation).
- `graph.json` — `BuildGraph` (nodes + edges; self-loops removed).
- `assets.json` — sorted vault-relative paths (with `/`) of the images the pages cite and that exist as files inside the vault. It is the whole allowlist of the image route (see Auth, data, config).
- `index.json` — page/folder counts + `builtAt` + `startedAt` (the moment just before the vault scan). It is written **last**, after the pages, the indexes, `graph.json` and the pruning, so a new `startedAt` means a build that finished.

Stale pages are pruned: after writing, the builder deletes every `pages/**/*.json` it did not write in this build (compared case-insensitively: on NTFS a case-only rename keeps the old file name on disk, and an exact comparison would delete the page just written) and removes empty folders. A build that found **zero** pages deletes nothing (empty vault folder, unmounted disk).

Types live in `builder/types.ts` and `types/index.ts`.

### Builder pipeline (`builder/pipeline.ts`)
Per page: dataviewjs/DQL are extracted, then a **recursive `renderBody`** runs in this order: dataview → `renderColumns` → `renderCallouts` → `applyObsidianCompat` → `renderCaptions` → wikilinks → `renderMarkdown` (remark/rehype). It's recursive (callouts/columns call `renderBody` on their stripped inner content) which is why dataview/columns/callouts nest correctly. **Order is load-bearing** — e.g. columns before callouts (fences are stronger boundaries than blockquotes); dataview inside `renderBody` so blocks nested in callouts/columns are reached after their `> `/fence prefixes are removed. Plugins are in `builder/plugins/`.

`--first <note path>` (repeatable; `buildVault(vault, { first })`) makes the builder render those notes first and write each `pages/<path>.json` right away, plus `pages-index.json` and `tree.json` once after the first one (same content and order the full build writes), then continue the normal build. Notes changed since the previous build's `startedAt` (`builtAt` in an old `index.json`) go in front too, newest first, after the explicit ones (`builder/first-pages.ts`); without a previous `index.json` only the explicit ones count. The front list is capped at **20**, so a cron run that rewrites hundreds of notes doesn't become "everything first". "Changed" is `noteTime` in `builder/scanner.ts`: `max(mtime, ctime, birthtime)`, ignoring timestamps in the future. `ctime` covers a rename in Obsidian (it keeps `mtime`) and `birthtime` covers a note copied into the vault (it keeps both). This is how the note a user just created is ready in about a second even though the whole-vault build takes several. During the front, `assets.json` is rewritten before each front page as the union of the previous one with the images resolved so far, so a new image opens together with its page; the final one is the exact list. Invariant: the output with `--first` is byte-for-byte the output without it (`index.json` aside).

**Child notes and tabs** (`builder/note-family.ts`). A note with `note_type: tab` or `note_type: comment` and `parent: "[[path/of/mother]]"` is a child note of that mother. Membership is by `parent` alone (the file's folder doesn't matter); it is a vault-root path matched exactly (the exact case first, then case-insensitively; no basename lookup), with or without brackets, dropping alias, heading, `.md` and a leading `/`. `parent` must be a quoted string: unquoted, YAML reads `[[X]]` as a nested list and the note has no `parent`. Only `.md` notes can be mothers. It applies to every vault.
- A child note is left out of the tree, the search and the graph (local and global, so it adds no backlinks): `pages-index.json`, `tree.json` and `graph.json` are built from the listed pages only, and a folder holding only child notes disappears from the tree. Dataview still sees every note, children included, and the link resolver is unchanged (a link to a tab opens it).
- A tab is a page of its own (`pages/<path>.json`), reached through its mother's tab bar. `PageMeta.tabs` is the bar, the same list on the mother and on each of its tabs: the mother first (labelled with its `tab_label`, else its title), then the tabs by `order` ascending (integers only; a tab without `order` goes last), ties by title (pt-BR collation), then by path. A tab's label is its title. One level only: a tab whose `parent` doesn't resolve (orphan), points to itself or to another child note (a tab of a tab, an A↔B cycle) is an ordinary note, visible and without a bar, so nothing disappears silently.
- A comment with a `parent` (resolved or not, even one outside the format such as a list or a number) gets no page and shows up nowhere on its own (its conversation is attached to the mother's page, see Comments below), so a comment body never goes through the full render (which runs dataviewjs): `pageCount` counts tabs but not comments, and the `--first` front never includes a comment. Without a `parent` it is an ordinary note.
- A note without a recognized `note_type` is written exactly as before (no `tabs` key).

**Comments** (`builder/comments.ts`, `builder/comment-render.ts`). The builder attaches `note_type: comment` notes, grouped into conversations, to the page they comment on.
- A page is **commentable** when it has a Properties block and is not a tab of a tab bar (an orphan tab is an ordinary note, so it can be commentable). Only then does its `PageMeta` get `commentable: true` and its HTML the marker `<div class="vault-comments-slot"></div>` (`COMMENTS_MARKER`) right after the Properties block, before the body: the viewer puts the comment strip there. Any other page has neither key nor marker and is written as before.
- Conversations follow `parent` (same resolution as child notes): a comment whose `parent` is a non-comment note is a **principal** comment of that note; one whose `parent` is a comment is a reply; a reply to a reply climbs to the principal, so the output has one level of replies. Orphans are dropped (still no page, attached nowhere): a `parent` that doesn't resolve at some step, a cycle, a reply under an orphan, and a mother that isn't commentable (a tab, a note without Properties).
- `PageMeta.comments` (only with at least one conversation) is `CommentThread[]`, `{ comment, replies }` of `PageComment { path, author, createdAt, updatedAt, body, html }`. `author` is the frontmatter `author` as text (`''` if absent). `createdAt`/`updatedAt` come from `created_at`/`updated_at` normalized to ISO UTC (`toISOString`), `null` when absent or not a date; an unquoted YAML timestamp is already a `Date` (its offset is lost), a quoted one is parsed. `body` is the raw markdown without frontmatter (for editing); `html` is the restricted render. Replies go by `createdAt` ascending; conversations by last activity (the latest `createdAt`/`updatedAt` in the conversation), newest first; `null` last, ties by path.
- **Nothing inside `_comments/` becomes a page or goes through the full render.** `_comments/` is the folder at the vault root where the viewer writes comments, matched case-insensitively, at any depth inside it; `Notes/_comments/x.md` and a root `_comments.md` stay ordinary notes. A valid comment there (`note_type: comment` with a `parent`) is handled as above. Any other `.md` there (a broken YAML frontmatter, which `extractFrontmatter` turns into `{}` plus the whole file as body, a half-written file, a missing or different `note_type`) is ignored: no page, no render, left out of the tree, the search, the graph, `pageCount` and the `--first` front (explicit or not), and never a mother, a tab or a step in a comment chain (a comment whose chain reaches one is an orphan). Dataview still sees those `.md` files. A `.canvas` there gets no page and no render either. It is a safety net: without it, a broken comment file would become an ordinary note and its dataviewjs would run.
- The builder ignores the vault's `comments` flag: comments and `commentable` are always in the output, and the flag is applied at request time (see Auth, data, config).
- Comment bodies are read again from disk when the mother page is rendered. A comment file that is gone by then (`ENOENT`, e.g. deleted while a build runs) is skipped, and a missing principal takes its whole conversation with it; any other error fails the build. The first pass (frontmatter of every note, right after the scan) still fails on a file that disappeared, as for any note; the rebuild that follows the deletion fixes it.
- `--first`: a mother's time for the front is the latest of its own and its comments', so a changed comment puts its mother in front. A comment itself never enters the front.
- The **restricted render** (`renderComment(md, { vaultSlug, resolveLink })`) is pure and synchronous, shared by the builder and the API routes. A comment body comes from users, so nothing in it becomes raw HTML or runs. It uses remark-parse + remark-gfm + a local plugin + remark-rehype **without** `allowDangerousHtml` (no rehype-raw, slug or math). Rules:
  - Raw HTML, inline or block, becomes escaped text. remark-rehype alone would drop it silently, so the plugin turns it into text.
  - dataview/dataviewjs fences are plain code, never run. Callouts are plain blockquotes.
  - Images (`![a](x)`, `![a][r]`) and embeds (`![[x]]`) come out as their literal markdown text.
  - GFM footnotes (the reference `[^1]` and the definition `[^1]: ...`) come out as their literal markdown text, with nothing inside the definition interpreted. remark-rehype would give them fixed ids (`user-content-fn-1`), which collide between comments and with the page, and would let a comment hijack in-page anchor navigation.
  - A link becomes `<a>` only with an `http`, `https` or `mailto` scheme, or a relative URL (the micromark `sanitizeUri` rule). Otherwise only its text stays, and a reference definition with an unsafe URL is dropped. `mdast-util-to-hast` doesn't check schemes, so the plugin does.
  - Wikilinks follow `replaceWikilinks`: href `/vault/<slug>/<encoded path>`, `#heading` slug, dead link `span.vault-dead-link`. They are built as tree nodes, so the alias is always escaped text; `replaceWikilinks` itself doesn't escape it, which is why it isn't reused here. The href goes in `hProperties` so remark-rehype's `normalizeUri` doesn't percent-encode accents in the fragment.
  - A single newline becomes `<br>`, and CRLF is normalized.
  - The tree is walked by hand: `unist-util-visit` is only a transitive dependency.

Notable plugin behaviors:
- **`dataview.ts`** runs vault DataviewJS in a Node `vm` with a mini-DOM shim (an `El` class, `dv.container`, `document`, `app`). Everything appends to ONE ordered `container` — do not reintroduce a separate output buffer (it scrambles section/gallery order). DQL and `dv.table/list` emit `.dataview-result` placeholder divs that the client hydrates into interactive tables.
  - `executeDataviewJS` is async. As in Dataview, a block containing `await` runs inside an async function, and `renderBody` replaces blocks one at a time (`replaceAsync` in `pipeline.ts`) so captured CSS keeps block order. Output is serialized once, so un-awaited `dv.view`/`dv.io.load` calls are awaited before serializing; the whole thing has a deadline (`timeoutMs`, default 30 s) because a promise that never settles would drain the event loop and make the builder exit 0 without writing anything.
  - `dv.view(name, input)` loads `<name>.js`, then `<name>/view.js`, compiles it **in the block's vm context** (same globals) and passes `(dv, input)`; `<name>/view.css` goes to the page CSS (once per page, even if the view throws). `dv.view` never rejects: every failure becomes an inline `.dataview-error`, so an un-awaited call can't become an unhandled rejection. `dv.io.load(path)` reads a vault-relative file and returns `undefined` when it is missing or resolves outside the vault (as in Obsidian, such a file doesn't exist). Both need `vaultRoot` in `executeDataviewJS`'s options.
  - DOM fidelity that shared renderers rely on: DOM properties that mirror attributes (`href`, `src`, `title`, `value`, …) and boolean ones (`open`, `disabled`, …) are accessors over `attrs`; `classList`; `document.createElementNS` (SVG serialized as-is). `dv.container` is serialized as an element **only** when the script touched it (class/id/attribute), so `.root .x` CSS works and untouched blocks keep their old output. `p.file.frontmatter` is the raw frontmatter; `Date` and `URL` come from the builder's realm so `instanceof Date` matches gray-matter dates.
  - There is no `window` in the context, on purpose: a script shared with Obsidian checks `typeof window` to leave out controls that only work with live events (e.g. a shared gallery renderer drops its reorder buttons and filter pills that way). A gallery participates in the viewer's filter bar by marking `.dv-gallery` / `.dv-card` with an `internal-link` (`data-href` = page path) inside the card.
- **`obsidian-compat.ts`** handles Obsidian-permissive markdown. For emphasis with inner spaces (`**x **`, `** x**`) it **normalizes the markdown** (moves the space outside the marker) and lets remark do the pairing, rather than emitting `<strong>` itself — emitting HTML breaks pairing in chains with links. Adjacency rules run after normalization and must not cross `[]()`.
- **`callouts.ts`** renders callout titles via the full `renderInner` (so titles support markdown/links), and tracks fenced-code regions so example callouts inside code blocks stay literal.
- **`properties.ts`** emits the frontmatter "Properties" block; its label is a `data-i18n` span relabeled client-side (see i18n). Values follow how Obsidian shows properties: a value that is, as a whole, an `http(s)` URL becomes an external link (checked before image detection, so a URL ending in `.png` is not taken for a vault image), and an unquoted YAML `true`/`false` (Obsidian's Checkbox type) becomes a read-only `<input type="checkbox" disabled>`, the same markup as a task list item; a quoted `"false"` stays text. `tab_label` is always hidden; `parent`, `note_type` and `order` are hidden only on a child note (`note_type` tab or comment) and stay ordinary properties on any other note (e.g. `note_type: character`).

### Viewer (`components/viewer/`)
Three panes: `SidebarPanel` (tree/search) · `ContentPanel` (page) · `GraphPanel` (local graph + ToC + backlinks, collapsible, state persisted in-memory across navigation).
- `lib/parse-html-segments.ts` splits `page.html` into `HtmlSegment[]` (extracting the banner as its own segment and splitting at `.dataview-result` placeholders); `ContentPanel` renders them and **memoizes** them so unrelated re-renders (lightbox, hover preview) don't reset native `<details>` state.
- `ContentPanel` also does plain-DOM enhancement: SPA link interception, external links → new tab, image/banner lightbox, mermaid render, the Notion-style gallery filter bar (a gallery left empty hides with its group title, or with the `<details>` group whose body is only that gallery — `lib/gallery-group.ts` — and the bar is inserted above that group, never inside it; the active filter chips are remembered per `pagePath`, so they come back when the bar is rebuilt for the same page (a `router.refresh()`) and reset on navigating to another one; an always-open Notion-style text search field, ANDed with the chips, that matches the card's visible text and every `data-props` value, never the note's content, ignoring case and accents, with all words in any order, and is remembered per page together with the chips: `lib/gallery-search.ts`; the field's focus comes back after a refresh of the same page; the bar shows with 4 or more `.dv-card`s, with props or not, and with only the search when no property fits a chip), and relabeling `[data-i18n]` nodes.
- The tab bar (`components/viewer/NoteTabs.tsx`) shows `PageMeta.tabs` at the top of the content pane, above the banner and the title, outside the memoized article segments. A plain click navigates SPA-style to the tab's own URL (`router.push`), so F5 keeps the tab; a modified or middle click is left to the browser. The active tab has `aria-current="page"`. On a tab's page the local graph and backlinks are empty (tabs aren't in the graph) and the sidebar highlights nothing.
- A note's `cssclasses` (list or space/comma string, `lib/css-classes.ts`) become classes on every `.vault-article`, as in Obsidian. Its width is `max-width: var(--file-line-width, 72ch)`, so a cssclass that sets `--file-line-width: 100%` in page CSS widens the page; `wide-page` still does too.
- Vault CSS written for Obsidian (a DataviewJS `view.css`, a gallery script's `<style>`) works because `app/globals.css` aliases Obsidian's variable names (`--background-secondary`, `--background-modifier-border`, `--text-normal`, `--interactive-accent`, `--font-ui-small`, …) to the viewer theme, and `ContentPanel` mirrors the next-themes theme onto `body.theme-dark` / `body.theme-light`.
- cytoscape graphs (`GraphCanvas`, `GlobalGraph`) cannot use CSS variables — colors are resolved at runtime via `getComputedStyle`.

### Auth, data, config
- Auth: JWT (`jose`) in the `vault_session` cookie, bcrypt passwords, `better-sqlite3` at `users.db` (schema auto-created in `lib/db.ts`). Users have admin/reader roles; non-admins get per-vault permissions (`vault_permissions`); admins see all.
- `users.display_name` (TEXT, `NULL` = no name) is an optional display name the admin edits; comments show it before `@username`. `lib/display-name.ts` validates it: trimmed, empty becomes `null`, at most 80 characters, no control characters. `applySchema` adds the column with `ALTER TABLE users ADD COLUMN display_name TEXT`, guarded by `PRAGMA table_info(users)`, so it is idempotent and an existing `users.db` is migrated the first time it is opened, with no separate migration step.
- Vault images are **not** under `public/`: the builder only lists them in `data/<slug>/assets.json`, and `app/vault-assets/[slug]/[...path]/route.ts` serves them straight from the vault folder, on the same URL the HTML carries (`/vault-assets/<slug>/<path in the vault>`). The route accepts only paths in that vault's `assets.json` (matched case-insensitively; read with an mtime-aware cache, so a new build is valid on the next request, no restart), then re-checks that the resolved file is a regular file inside the vault with an image extension. Anything else is 404. Why not `public/`: `next start` lists `public/` **once, at boot**, so an image copied afterwards answered 404 until a restart, and copying thousands of images made the build several times slower and duplicated gigabytes.
  - Auth is in two places on purpose: `proxy.ts` checks first (session; for readers, permission on the vault via `lib/asset-guard.ts`, on the decoded path with a case-insensitive `/vault-assets/` prefix — the host filesystem is case-insensitive — and the slug as written, since grants hold the configured slug), and **the route checks again** (401 without a session; 404 for a reader without permission, so "no access" can't be told from "doesn't exist"). The proxy is no longer the only gate. **The proxy matcher must not exclude images or `vault-assets`**: until 2026-11-13 it did, and every vault's images were public.
  - The handler reads the whole file and has its own `HEAD`: Next derives `HEAD` from `GET` and discards the body without cancelling the stream, which leaked a file descriptor per request. Headers: `Cache-Control: private, no-cache` (the browser revalidates with `ETag`/`Last-Modified`; a shared cache must not keep an image that needs a session), `X-Content-Type-Options: nosniff`, and for SVG a restrictive `Content-Security-Policy` so an SVG opened in its own tab can't run script on the viewer's origin.
  - Consequences of listing only what pages cite: if the vault's disk is offline its images disappear while the pages stay, and a renamed image is 404 until the next build.
  - **Deploy:** delete the old `public/vault-assets/` **before** the server starts. If it exists at boot, the old copies enter Next's list and are served ahead of the route, ignoring `assets.json` and its permission check. Order: run the new builder on all vaults (`--all`; the old server keeps serving the old copies, same URLs), `npm run build`, delete `public/vault-assets/`, restart. Images answer 404 for a few seconds between the last two steps.
  - `images.unoptimized` keeps `/_next/image` (unused) from serving them by another route.
- `better-sqlite3` ≥ 13 is N-API, so its binary survives Node upgrades; 12.x was tied to one Node ABI and broke login (HTTP 500) when the host's Node changed. Its install script is denied in `allowScripts` on purpose: the package ships prebuilt binaries, and the script would only recompile from source.
- Build state (`getBuildState`, the queue behind `runRebuild`) lives in an object on `globalThis` under `Symbol.for('vault-viewer.rebuild')`, not in a module variable. Turbopack runs **pages** and **route handlers** in two separate runtimes (`chunks/ssr/[turbopack]_runtime.js` vs `chunks/[turbopack]_runtime.js`), each with its own `moduleCache`: a page importing `lib/rebuild.ts` would get another module instance, would not see a build started by the internal route, and could run a second build of the same vault at once. Per vault it holds `running` (with `startedAt`), `queued`, the `first` paths of the queued build, and `lastAttemptStartedAt` (start of the last build that ended, **successful or not**). `runRebuild(slug, { first })` passes each `--first` as its own spawn argument; a request joined to a running build puts its `first` into the extra build.
- **Pending pages** (`lib/pending-page.ts`): content newer than the last build must not be a 404 or a silently stale page. For a page path `p` (the decoded URL path for a page that doesn't exist; `page.path` for one that does; synthetic folder pages are out), the page is pending when: `p` is safe (no `..`, `\`, empty or dot-leading segment, none of the characters Windows rejects); `<p>.md` or `<p>.canvas` exists in the vault and the scanner would visit it (`isScannedPath`, the same `.viewerignore` predicate); and `t = noteTime(stat)` is newer than what a build has seen. A running build that started after `t`, or a queued one, only has to be waited for. Otherwise, if `t > lastScan`, the page **requests a build** with `first: [p]` (fire-and-forget). `lastScan = max(index.json.startedAt ?? builtAt, lastAttemptStartedAt)`; the second term is what stops a loop: a note the builder can't generate, or a build that fails, costs **one** build and then falls to 404 (or to the page as it is). Within the pending rule, only the page triggers builds (the internal rebuild route and the admin also do, for their own reasons). `GET /api/vault/[slug]/page-status?path=<p>` (same auth as `preview`, `Cache-Control: no-store`, `{ state: 'ready' | 'pending' | 'missing' }`) only reads, and treats a page JSON that doesn't parse (read mid-write) as absent, never `ready`. A page JSON newer than `t` is already the new version and skips the rule.
  - Windows path aliases bypass a textual `.viewerignore` check: NTFS stream syntax (`Name::$INDEX_ALLOCATION`), 8.3 short names, trailing dot or space, and folder links. So `noteFor` also requires the **canonical** path (`realpath`) of the file to equal `<p>.md`/`.canvas` case-insensitively. This matches `walkVault`, which doesn't follow folder links.
  - UI (`app/(app)/vault/[slug]/[[...path]]/page.tsx` + `components/viewer/PageStatusNotice.tsx`): a missing-but-pending page renders the normal viewer with a provisional page ("this page is being generated…"); an existing-but-stale one renders as is with an "updating this page…" strip. `PageStatusNotice` polls the status route (every 1 s for the first 30 s, then every 5 s, giving up after 5 min, the same value as `REBUILD_TIMEOUT_MS` but its own constant, `POLL_GIVE_UP_MS`) and calls `router.refresh()` on `ready` or `missing`. The refresh is capped (at least 5 s between two, at most 3 per mount; `lib/page-status-poll.ts`) so a status that never settles can't refresh forever. Open `<details>` may reset on the refresh; the refresh is expected to keep the scroll position. On giving up, the wait screen shows "reload later", while the "updating…" strip just disappears without a message.
- **Open tab refreshes itself** (`lib/page-version.ts`, `lib/page-watch.ts`, `components/viewer/PageWatcher.tsx`): when a rebuild changes the page a tab shows, the tab calls `router.refresh()` on its own. The version of a page is the sha1 of the `JSON.stringify` of its `PageMeta` (`pageVersion`), which `page.tsx` computes on the very object it renders; the file mtime is not usable because the builder rewrites every page JSON on every build, changed or not. `GET /api/vault/[slug]/page-version?path=<p>` (same auth as `page-status`, `no-store`) answers `{ version: string | null, building: boolean }` from disk (`currentPageVersion`, cached by mtime and size; `null` for an unsafe path, a missing page or a JSON that doesn't parse; folder pages are hashed from the synthetic page). `PageWatcher` creates the watcher inside its effect (`stop()` is terminal and StrictMode runs effect, cleanup, effect) and feeds it `visibilitychange`, `focus` and the user's interactions.
  - Cadence (`createPageWatcher`): a hidden tab polls nothing; coming back (or focus) checks right away (deduped within 1 s), then waits 0.5 s, 1 s and 1.5 s between the next checks (`RETURN_RAMP_MS`, so at 0.5, 1.5 and 3 s), then every 2 s until 20 s after the return; each return restarts the ramp; while a build is running or a newer version is waiting, every 2 s (the build part capped at 5 min); otherwise every 60 s.
  - Refresh only when the version differs from the rendered one, and never twice in a row for the same version (it only remembers the version it last refreshed for, so content that goes back to an older version later still refreshes), no more than once every 5 s. It is postponed while the user is busy: the filter menu (`.dv-filter-menu.is-open`) is open, or focus is in an editable field (text-like `input`, `textarea`, `select`, `contenteditable`) with an interaction in the last 3 s (`isUserBusy`). A failed check (network, non-ok, a body of the wrong shape, or no answer within a 10 s fetch timeout) counts as no news: it changes nothing and doesn't refresh. `building` means a build running or queued in this server process (`getBuildState`); a build run from the CLI (`npx tsx builder/index.ts`) isn't seen as building, so an open tab picks it up on its next check (on return to the tab, or within 60 s while visible).
  - Refreshing without a change is avoided on purpose: React 19 reapplies `innerHTML` for every new `page` object, so a refresh with identical content would make the page flicker.
  - A pending page (generating or updating) is left to `PageStatusNotice` and isn't watched, and neither is a page while the global graph is open (a refresh would rebuild the graph and lose zoom and position; the watcher remounts and checks right away when it closes). A note that disappeared gets no refresh (`version: null` is never "news").
- Builds run through `lib/rebuild.ts` (`runRebuild`): the builder is spawned as `process.execPath --import tsx builder/index.ts`, without a shell (`spawn(cmd, args, { shell: true })` is deprecated, DEP0190), one build at a time per vault; requests arriving during a build coalesce into ONE extra build (`wait: true`, used by the admin route and by the internal route with `?wait=1`, resolves with that extra build's result). A build that throws (its promise rejects instead of settling through the child's events or the timer) counts as a failed build, handled exactly like one that exits non-zero: its result is `ok: false` with the error message as `output`, `lastAttemptStartedAt` is recorded and the lock is released (or the next extra build starts), so a failing build never makes `runRebuild` reject.
- `POST /api/internal/rebuild/<slug>` (header `X-Rebuild-Key` = `INTERNAL_REBUILD_KEY`) lets the external sync service trigger a rebuild. `proxy.ts` lets `/api/internal/` through without a session, so the route authenticates itself, in this order: `cf-connecting-ip`/`forwarded`/`x-real-ip` present, or `x-forwarded-for` with a non-loopback IP (Next injects it with the socket address on every request, so its mere presence proves nothing) → 403; `Host` not loopback (`127.0.0.1`, `localhost`, `[::1]`, any port) → 403; env var unset → 404; wrong/missing key → 401 (SHA-256 digests + `timingSafeEqual`); invalid slug → 400; vault not in `vaults.config.json` → 404; else 202 without waiting for the build. With `?wait=1` (exactly `1`; no parameter or any other value keeps the 202), it answers only when the build that covers the request ends, i.e. `runRebuild(slug, { wait: true })`: with a build already running, that is the extra build queued after it. 200 `{ ok: true }` if that build succeeded, 500 `{ ok: false }` if it failed or hit `REBUILD_TIMEOUT_MS`; the build output goes to the log, never to the body. A client that gives up and disconnects (the sync service waits 15 s after creating or resyncing a note) cancels nothing: the build runs to the end and its result is dropped. The no-wait 202 is what the sync service's 60 s debounce uses, so it must not change. Security depends on: the viewer listening on loopback only; the reverse proxy forwarding the original `Host` (a `header_up Host` rewrite defeats the check); and the caller using `127.0.0.1`/`localhost`.
- `vaults.config.json` (gitignored — copy from `vaults.config.example.json`) defines vaults; read via `lib/vault-config.ts` with an **mtime-aware cache** (re-reads when the file changes, so the admin UI and routes stay consistent without a restart). Per-vault `titleProperty` / `coverProperty` / `homePage` drive the builder. Per-vault `comments` (boolean, off by default) turns comments on for that vault. The builder ignores it; the viewer and the API apply it at request time. `page.tsx` doesn't strip comments from the `PageMeta` when it is off.
- **Display names at request time** (`lib/comment-authors.ts`):
  - When the vault's `comments` flag is on and the page is commentable, `page.tsx` resolves the comment authors and the logged-in user to display names (`dbGetDisplayNames`).
  - It passes the map as the `displayNames` prop of `VaultViewer`, **outside** the `PageMeta`. `pageVersion(page)` must hash exactly the JSON on disk, as `currentPageVersion` does; names inside the `PageMeta` would make every check see a new version, and the open tab would refresh in a loop.
  - A username missing from the map is unknown to the database; `null` means a user without a display name.
- The admin UI (`/admin`) edits users and vaults and can trigger a rebuild by spawning the builder (`app/api/admin/vaults/[slug]/rebuild`).
- `.viewerignore` (gitignore syntax) at a vault root hides files/folders from the build — applied in `builder/scanner.ts` via `builder/vault-ignore.ts`. The image route does not apply it: an image in an ignored folder cited by its full path is still served (deliberate decision).

### i18n (`lib/i18n/`)
Flat dictionaries per locale (`en.ts`, `pt-BR.ts`); add a language by copying a file and registering it in `index.ts` `LOCALES`. The active locale is resolved in `app/layout.tsx` from the `vault_locale` cookie or `Accept-Language` (fallback `en`). Client components use `useI18n().t(...)`; server components use `await getT()`. Strings the builder bakes into HTML carry a `data-i18n` attribute and are relabeled client-side, so locale switching needs no rebuild.

## Testing
Vitest, node environment (jsdom is available for DOM-dependent tests). Tests in `tests/` mirror `builder/` and `lib/`. Builder plugins are pure functions tested directly; prefer adding a focused test next to the plugin you change.
